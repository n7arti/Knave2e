Reference for human and AI authors writing a RuleSystemSchema manifest.

For design rationale (why fields are shaped this way, why hooks are deprecated, why the layout vocabulary is closed, etc.) see the engine design notes (not published; ask the user if a rationale matters). This document is a reference manual; it describes what the schema looks like, not why.

Companion: machine-readable JSON Schema via exportManifestJsonSchema() (the live validation schema of the product). For a practical product route, start with the authoring process.

Last update: 2026-08-20 — reconciled the manual with the live schema and authoring UI: catalogs, action groups, initiative, combat defaults, item and damage rules, equipment, FX, slot lists, preview metadata, current field / resource variants, sheet variants and vision.

A rule system is a single JSON document validated by Zod (RuleSystemSchema). It declares: fields & groups, resources, derived formulas, auto-modifiers, data-scope permissions, catalogs, actions, conditions, combat defaults, equipment, sheet variants and layout, vision, dice/FX presentation, and migrations. Once loaded through the pipeline (loadBuiltinSystem(id) or loadManifest(raw)), the manifest is the only source of truth for that system — runtime reads come from here.

1. Manifest top-level shape

{

  "id": "dnd5e-srd",              // stable system id
  "name": { "en": "...", "ru": "..." },
  "version": "1.0",               // your system's content version (semver)
  "description": { "en": "..." },

  // Optional overlay metadata (homebrew built on top of another system)
  "baseSystemId": "dnd5e-srd",
  "expectedBaseSystemVersion": "1.0",

  // Content
  "fieldGroups":       [...],

  "derivedFields":     [...],
  "autoModifiers":     [...],
  "slotLists":         { ... },
  "dataScopes":        [...],

  "entryConventions":  { ... },
  "noteFolders":       [...],
  "actions":           [...],
  "actionGroups":      [...],
  "conditions":        [...],
  "bonusCategories":   [...],

  // Presentation
  "sheetLayout":    { ... },       // declarative fallback layout

The per-document /systems UI currently edits the common slots through ten pages. Some valid advanced slots (critRule, initiative, itemRules, damageCascades, stateRules, equipment, fx, editorMeta) have no dedicated page yet. The schema accepts them and runtime consumers use them; the absence of a page is an authoring-UI limitation, not a different manifest format.

Notes: "$comment"

JSON has no comments. A note — a reminder for later, or a block set aside — is a "$comment" key in any object of the manifest, with any value:

{
  "type": "resourceList",
  "$comment": "Классовые ресурсы; Метку охотника вернуть, когда появится следопыт",
  "include": ["laying_hands", "inspiration_bard"],
  "presentation": "grid"
}

The loader and the /systems editor drop every $comment before checking the shape, so the key never fails a strict schema and no part of the system reads it; the stored definition keeps it, and the editor's JSON views save it back. A block set aside goes in as a value — "$comment": { "type": "heading", "text": "…" }. Only the exact name $comment is a note; any other unknown key is not.

Notes belong to the manifest. The /systems action editor checks an action without its notes. Its JSON view keeps every note. The structured form keeps the notes of what it edits in place (the action, step fields, the cost, the icon); the crit, repetition, duration and animation settings rebuild their objects, and notes inside those go with an edit there (as does clearing the icon's glyph). Applying a template replaces the whole action, notes included. An action at the table — its JSON editor, a token's actions — and a compendium entry refuse notes.

2. Identity

Key Type Notes
schemaVersion '1.0' | '1.1' | '1.2' | '1.3' Engine-version of the manifest shape itself. 1.3 adds semantic entryList presentation and narrow legacy projections for versionless entry data.
id EntityId 1–64 letters (any language), digits, _ or -; not starting with _, not digits only, no dots or spaces. Stable across versions.
name I18nLabel string | { en, ru, ... }. Non-empty record. The system's only name: the systems sidebar, the room's system picker, the catalog and the editor header all show it (since 2026-10-01; the server keeps a one-language copy, ru → en, for search). A copy is named <name> (by <copier>).
version semver 'MAJOR.MINOR(.PATCH)?' Content version. Bumped when fields/actions/conditions change.
description I18nLabel? Long-form for catalog. The system's only description, like name.

3. I18nLabel

Either a plain string (system-implicit locale) or a record { <localeCode>: string }:

"label": "STR"
"label": { "en": "Strength", "ru": "Сила" }
"label": { "en-US": "Color", "en-GB": "Colour", "ru": "Цвет" }

Locale codes: [a-z]{2,3} optionally - and [A-Z]{2}. Empty record rejected.

4. Field groups & fields

"fieldGroups": [
  {
    "id": "abilities",
    "label": { "en": "Abilities", "ru": "Характеристики" },
    "layout": "grid-6",            // 'vertical' | 'inline' | 'grid-3' | 'grid-6' | 'skill-list' | 'table'
    "scopeId": "abilities",         // optional ref to dataScopes[].id
    "fields": [...]
  }
]

Field types

type Stored as Notes
number number Honours min, max.
text string Single-line.
textarea string Multi-line.
tag-list string[] Catalog-backed multi-select or free-form tags.

text + catalogId renders a single-select; tag-list + catalogId renders a multi-select. allowCustom: true permits values outside the catalog. Input modes are presentation variants over these storage shapes, not new field types. A text field may also take its value from a compendium article — see Articles for fields and sections.

Field shape

{
  "key": "str",                   // DataKey: [a-z][a-z0-9_]{0,63}
  "label": { "en": "Strength" },
  "description": { "en": "Physical power." }, // optional help text
  "shortLabel": "STR",            // for compact / grid layouts
  "type": "number",
  "default": 10,
  "min": 1,
  "max": 30,
  "width": "half",                // 'full' | 'half' | 'third'
  "derivedKey": "str_mod",        // ref to derivedFields[].key
  "derivedFormat": "{v}",         // the sheet signs numbers itself: '{v}' → "+3"; '+{v}' → "++3"
  "rollFormula": "1d20+str_mod",
  "rollLabel": { "en": "STR Check" },
  "inputMode": "dot-track",       // see inputMode list below
  "tags": ["core"],               // free-form tags for ordering/filtering
  "articles": { "tags": [["Тип: Класс", "Type: Class"]] } // text only: see Articles for fields and sections
}

A number field's value may be a formula; its total may be pinned

A number field's default — and the value stored on a token — may be a formula string instead of a number: "default": "10 + dex_mod" gives an unarmoured AC that follows Dexterity. It is computed by the same engine as an effect's value (no dice; names the sheet does not know make it not apply) and is the field's BASE: effects stack on top, a «replace base» effect (armour) replaces it while active. A formula naming its own field reads nothing there.

A token's total may be pinned: token_<id>_overrides[key] — a number or a formula — wins over the base and every effect; in a formula, the field's own name reads the base with effects. On the sheet both are written from the field: Основа / Итог while it is focused, «Зафиксировать» / «Снять» in its breakdown card. Through the bridge both are patch_state writes to token_<id>_system and token_<id>_overrides; remove a pin by writing the overrides object without the key.

Сравнение в rollFormula считает кубы, не сумму

4d6>3 — это «сколько костей выше 3», то есть пул успехов, а не «сумма больше трёх». На d6 запись 4d6>8 даёт ноль всегда. Сумму сравнивает группа: {4d6}>8 вернёт 1 или 0. Скобки — арифметика, (4d6)>3 парсер не принимает; пробелы вокруг сравнения ломают разбор.

Если системе нужен итог и решение по нему — сравнение выносится из формулы: в действии это ветка по result, у атаки roll.compare, у проверки её порог. Подробнее — the engine design notes (not published), раздел «Сравнение в формуле».

inputMode

  • 'default' — plain input matching type.
  • 'checkbox-list' — catalog-backed tag-list as one checkbox row per entry.
  • 'dot-track' — a single glyph cell that cycles a configurable palette (glyphs, default ['○','●','◆']). The value indexes into the palette; a value past it (but within max) shows as a plain number. Use for enum-like ladders — D&D proficiency (none / proficient / expertise).
  • 'linear-dots' — a linear row of field.max round dots, first value filled. Use for dot ratings — WoD attributes (max=5), Blades action ratings (max=4). Click a dot to set the rating; click the last filled dot to drop by one.
  • 'segmented-track' — like linear-dots but squares, for tally-of-slots trackers (D&D death saves, ammo segments, charges).
  • 'status-track' — a row of max cells, each independently cycling a named-glyph palette (statuses). Use for WoD health / willpower (empty / superficial / aggravated / full). Stored as string[] of status names (declare type: 'tag-list'); the engine exposes per-status counts to formulas as <fieldKey>_<status> (see statuses below).
  • 'readonly-derived' — shows the derived value only. Use for computed displays (proficiency bonus, ability modifiers, calculated AC).
  • 'scale-track' — compact scale/rating presentation supported by the current field renderer; keep numeric bounds explicit.

dot-track / linear-dots / segmented-track store an integer 0..max; status-track stores a string[]. Step / roll semantics come from derivedFields that consume the value(s), not from the input mode.

glyphs

Palette for inputMode: 'dot-track', e.g. ["○","●","◆"]. The value indexes into the array; beyond it the value renders as a plain number. Defaults to ["○","●","◆"]. Ignored by other input modes.

statuses

Named-glyph palette for inputMode: 'status-track'. Each cell cycles through the list on click; the first entry is the empty/default cell.

"type": "tag-list",              // status-track stores string[]
"inputMode": "status-track",
"max": 10,
"statuses": [
  { "glyph": "□", "status": "empty",       "label": { "en": "Available" } },
  { "glyph": "/", "status": "superficial", "label": { "en": "Superficial" } },
  { "glyph": "X", "status": "aggravated",  "label": { "en": "Aggravated" } },
  { "glyph": "■", "status": "full",        "label": { "en": "Unavailable" } }
]

status must be identifier-safe ([a-z][a-z0-9_]*) and unique within the field — it becomes the formula key <fieldKey>_<status>. For a field health the engine puts health_empty, health_superficial, health_aggravated, health_full (counts) into formula scope, always present (0 when absent):

"derivedFields": [
  { "key": "is_dead", "formula": "health_aggravated >= health_max" }
]

sort (for status-track)

Optional. 'none' (default) keeps cells in the order the user clicked them. 'left' / 'right' press the filled cells against that edge, grouped by their position in statuses: the last-declared status sits at the edge, the empty one (first in statuses) fills the far side.

"statuses": [ /* empty, superficial, aggravated, full */ ],
"sort": "left"    // → ■ ■ ■ ■ X / / □ □ □   ("right" mirrors it)

The pre-rename 'start' / 'end' still load: they named where the empty cells went and are rewritten to 'right' / 'left', which keeps the sheet looking the same.

Sorting is order-only — it never changes the per-status counts, so the <key>_<status> formula keys are identical regardless of sort.

tags

Free-form, system-defined. Inspector ordering, filtering, layout-DSL node selection all consume tags. Common values: 'core', 'combat', 'reference', 'narrative', 'gm-only'. Engine doesn't interpret — your system chooses.

5. Resources

Resources are either scalar current/max pools (HP, mana, stress, spell slots) or 2–3-stage cascades. The layout-DSL resourceBar node consumes the same declaration as action steps and automatic refresh.

"resources": [
  {
    "key": "hp",
    "label": { "en": "HP" },
    "color": "#e74c3c",
    "currentKey": "hp",
    "maxKey": "hp_max",
    "maxDerivedKey": "hp_max_calc", // formula max until manually overridden
    "tempKey": "hp_temp",         // optional bonus pool
    "recharge": "long-rest",
    "refresh": [{ "trigger": "combat-end", "amount": "full" }],
    "visibleTo": "all",
    "displayIn": ["header", "sheet"]
  }
]

For kind: "scalar" (the default), currentKey and maxKey are required. maxDerivedKey references a derived field: the computed maximum is used while maxKey is empty; writing a max creates an explicit override.

A cascade does not declare top-level current/max/temp keys:

{
  "key": "army",
  "label": { "en": "Army" },
  "kind": "cascade",
  "stages": [
    { "currentKey": "front",   "maxFormula": "front_max",   "onEmpty": "cascade" },
    { "currentKey": "reserve", "maxFormula": "reserve_max", "onEmpty": "fail" }
  ]
}

refresh[] is the runtime cadence (turn-start, turn-end, round-start, round-end, short-rest, long-rest, combat-start, combat-end) and may restore full or a formula amount. It is distinct from recharge: recharge groups resources for an explicit restoreAllOf action.

recharge policy

Closed enum: 'manual' | 'short-rest' | 'long-rest' | 'dawn' | 'turn'. Default 'manual' — resource only moves via explicit consume/restoreResource steps. Other values mark the resource as a member of a recharge group that restoreResource: { restoreAllOf: … } actions can refill in one step.

{ "type": "restoreResource", "restoreAllOf": "long-rest" }

This is the canonical way to declare D&D long_rest: one step restores HP + spell slots 1-9 + hit dice (every resource whose recharge matches). Single-resource form ({ resourceId, amount, mode }) still works — XOR with restoreAllOf enforced at load.

Kind of resource: category, rank, resourceCategories

A resource's key is the name it is stored under; its kind is what it means. Spell slots of every circle and a warlock's pact slot are one kind:

"resources": [
  { "key": "spell_slots_3", "label": { "ru": "3 круг" }, "currentKey": "spell_slots_3_value",
    "maxKey": "spell_slots_3_max", "category": "spell_slot", "rank": 3 },
  { "key": "pact_magic", "label": { "ru": "Магия договора" }, "currentKey": "pact_magic_value",
    "maxKey": "pact_magic_max", "category": "spell_slot", "rank": "pact_magic_level" }
],
"resourceCategories": {
  "spell_slot": { "label": { "ru": "Ячейка заклинаний", "en": "Spell slot" }, "icon": "sparkles" },
  "action":       { "label": { "ru": "Действие", "en": "Action" } },
  "bonus_action": { "label": { "ru": "Бонусное действие", "en": "Bonus action" } },
  "reaction":     { "label": { "ru": "Реакция", "en": "Reaction" } }
}
  • category — a DataKey (lowercase Latin, digits, _): a reaction names the kind as a string literal and compares it character by character, so a stray capital or space would silently never match.
  • rank — the rank inside the kind: an integer, or a formula over the sheet of whoever owns the resource (the pact slot's circle grows with the warlock). The loader checks the formula like any resource formula.
  • Entry resources (entryConventions.<type>.resources[]) and table resources (table.resources[]) take the same two fields.
  • resourceCategories — the system's dictionary of kinds: a label for the spend chip's hint and a Lucide icon for the chip. The dictionary is open: name your own kinds. Use the conventional names where the kind is the same — spell_slot, ki, sorcery_point — so reactions from shared compendiums work across systems.
  • Four kinds are the turn economy: action, bonus_action, reaction, movement. Declaring one of them in resourceCategories turns on the turn marker on action cards in combat: the action's kind (active, bonus, reactive-*) or an explicit cost of a turn resource of that kind. Their shape and colour belong to the platform (green circle — action, orange triangle — bonus action, violet diamond — reaction, yellow footprints — movement); the dictionary gives only the label. A system without turn economy declares none of them and gets no marker.
  • No colour per kind: on the chip, colour means the state of a spend (returned, waived, short), never its kind.

6. Derived fields — formula language

Declarative pure formulas. Evaluated topologically; cycles fail at load.

"derivedFields": [
  {
    "key": "str_mod",
    "label": { "en": "Strength modifier" },
    "description": { "en": "Modifier derived from the Strength score." },
    "formula": "floor((if(str, str, 10) - 10) / 2)"
  },
  {
    "key": "save_str",
    "label": { "en": "Strength save bonus" },
    "description": { "en": "Strength modifier plus proficiency when trained." },
    "formula": "str_mod + if(save_str_prof, save_str_prof, 0) * proficiency_bonus"
  }
]

The formula language is total — no loops, no recursion, terminating in all cases. Built-ins: floor / ceil / round / abs / max / min / clamp / sum / len / has / if, plus var-aware contains(fieldName, id) and sum_matching(prefix). References to scalar fields use bare names. A tag-list is queried through contains('field_key', 'entry_id'), because an array does not become a scalar formula value. Dice notation is not allowed in derived fields — they must be deterministic.

label and description remain schema-optional, but every derived value that appears in a player-visible formula should declare localized versions. The formula-help UI and derived-value breakdown replace identifiers such as save_dex with these labels; built-in function names are localized by the application. The executable formula is never translated, so manifests must continue to use the stable DSL identifiers shown above. Help navigation is limited to four levels and detects cycles.

Save terminology and formulas (schemaVersion: 1.2)

"abilities": [
  { "key": "dex", "label": { "en": "Dexterity" }, "saveFormula": "1d20 + save_dex" }
],
"combatPresentation": {
  "save": {
    "label": { "en": "Save" },
    "description": { "en": "A roll made to resist or reduce an effect." },
    "difficultyLabel": { "en": "Difficulty" },
    "difficultyDescription": { "en": "Meet or exceed this value to succeed." }
  }
}

Declare saveFormula when a save includes proficiency or uses non-default dice. If omitted, the resolver keeps the legacy d20 + <ability>_mod fallback. The presentation block changes terminology/help only; mechanics remain in the action save step and ability formula. See the engine design notes (not published) for the pending-card override and visibility contract.

Lookup-table form

For table-style derivations (piece-symbol, multiclass spell slot tables, ability-modifier ladder) authors use an object formula instead of a string. Resolver reads the match keys from data, joins their string-coerced values with ., looks the composite key up in lookup, falls back to default.

{
  "key": "piece_symbol",
  "formula": {
    "match": ["color", "piece"],
    "lookup": {
      "white.king": "♔",
      "white.queen": "♕",
      "black.king": "♚",
      "black.queen": "♛"
    },
    "default": "?"
  }
}

The lookup form replaces the manifest.hooks.computeDerivedHook escape hatch for table-shape derivations. Numbers / booleans coerce to stable string segments — {class: 'fighter', level: 5} → 'fighter.5'.

7. Auto-modifiers — visual badges from system data

Four primitives are accepted: hp-bar, counter, status, and status-list. The last one projects every id from a string[] field through the condition catalog.

"autoModifiers": [
  {
    "type": "hp-bar",
    "source": { "currentKey": "hp", "maxKey": "hp_max", "tempKey": "hp_temp" },
    "visibility": "all"
  },
  {
    "type": "counter",
    "source": { "currentKey": "spell_slots_1", "labelTemplate": "L1: {spell_slots_1}" }
  },
  {
    "type": "status",
    "source": { "labelTemplate": "Dead" },
    "predicate": "hp <= 0",
    "visibility": "evident",
    "anchor": "center"
  },
  {
    "type": "status-list",
    "source": { "currentKey": "active_conditions" },
    "list": "conditions"
  }
]
  • predicate — boolean expression like 'hp <= 0', 'temp > 0'. When false, modifier is hidden. Variables come from systemData + derived.
  • anchor — 'top' | 'bottom' | 'left' | 'right' | 'center'. For hp-bar and status-list, leave anchor out unless the system needs its own layout: the product's standard layout then places them. (This is the engine default, not the room standard — a sample token a master saved in the room is applied on top of it and wins.) A token created from 2026-10-19 gets the bar on the top edge with its number on the bar, the name resting on the bottom edge, and statuses in two columns inside the token: debuffs down the left edge, buffs and then neutral down the right. A column has four places; with five or more statuses it shows three and «+N». Tokens created earlier keep their original look exactly, including rows that first appear later (first HP, first status). A row with an explicit anchor (and offsetX/offsetY) is hand-placed: it keeps that placement and the original look — number under the bar, statuses in a grid — and wins over the standard layout in every system, forks included. Use it for layouts the standard cannot express, such as two stacked gauges.

Token look fields and the look edition

The standard layout is made of ordinary modifier fields, visible in a token's modifiers when you read it through the bridge:

  • hp-bar.config.textPosition (and stat display: { type: 'bar' }) — 'on' | 'right' | 'left' | 'above' | 'below': where the bar's number stands. Absent = 'below'. The same rules hold for both gauges: 'on' keeps the bar within the middle of the token (between the status columns) and shrinks a long number to fit; a number with ANY chosen place hides below 7 screen px while the bar stays; a bar without the field draws its number at every zoom, as before.
  • name label (id: 'name-label'): anchorAlign: 'end' (the text rests on the anchor instead of hanging from it), color: '#ffffff' and the label's own outline, no plate. plate: true draws a theme plate behind a single-line label (an empty color then follows the theme); the default name no longer carries it (2026-10-20), and a name with exactly the shipped pair (plate: true, color: '') loses the plate and gets #ffffff when the master opens the room or places a token from such a source; a plate with its own colour stays. The default name keeps its size (fontSizePct: 17) and runs wider than a narrow token: since 2026-10-20 it does NOT carry fitWidthPct / minFontSizePct. A manifest may still set them on a label (the size then shrinks from fontSizePct down to the minimum to fit the width together with the plate, never cut). A name that carries exactly the pair shipped for a few hours on 2026-10-20 (fitWidthPct: 100, minFontSizePct: 13) loses it when the master opens the room; other values stay.
  • How rows attach to the token — the name's anchorAlign/plate/fit, the bar's textPosition with its fontSizePct, the cluster's layout — travels with the HUD LAYOUT when a master copies it (with the edition mark), not with the style alone. The name's color and its size group (fontSizePct with fitWidthPct/minFontSizePct) go with its plate: a style copy between a plated and a bare name keeps the target's; a layout copy brings them only when it changes the plate. Rows drawn inside the token (name on the lower edge, top-edge bar, columns) give a single click to the token; their editor opens on double or right click.
  • status-cluster.config.layout: 'polarity-columns' — the two columns above; anchor and offset do not move them.
  • meta.tokenPresentationRev — the token's look edition, written when the token is created: 2 for a new token (and for one placed from an actor or a compendium entry without its own HUD), absent = 1 for older tokens. A token placed with its source's own HUD takes the source's edition: a compendium snapshot carries the token's meta (no mark = 1), also when it is placed under the room standard; an actor's prototypeToken may carry tokenPresentationRev: 1 | 2 (not a token prop; absent with rows = 1). Rows a system adds later follow the token's edition — an old token keeps the old places even for a first HP bar. Copying the HUD layout from another token hands over that token's edition. A token you create through the bridge from scratch gets edition 2; one placed from an actor (place_token_from_actor) or a snapshot gets its source's edition as above. Do not write this key yourself.
  • visibility — 'all' | 'evident' | 'master' | 'owner'. evident remains visible on a token whose characteristics are hidden.
  • status-list.list — optional reference to a named slotLists entry. Without it, anchor/offset stepping is used.

Slot lists for repeated token badges

slotLists declares geometry for a stable sequence of badges. It is consumed by autoModifiers[type=status-list] and is unrelated to equipment slots.

"slotLists": {
  "conditions": {
    "anchor": "right",
    "baseOffsetX": 8,
    "baseOffsetY": 0,
    "stepX": 0,
    "stepY": 28,
    "capacity": 5
  }
}

capacity is advisory: overflow continues past it and can be reported by the UI. Runtime keeps first-free stable occupancy per token, so adding one status does not reshuffle every existing icon.

8. Data scopes — field-level permissions

"dataScopes": [
  {
    "id": "abilities",
    "label": { "en": "Ability Scores" },
    "keys": ["str", "dex", "con", "int", "wis", "cha"],
    "editableBy": "owner",        // 'master' | 'owner' | 'all'
    "visibleTo":  "all",
    "hiddenFromOwner": false      // optional: GM-only metadata override
  }
]

Field groups reference scopes via scopeId. Runtime checks gate every read and write through canViewField / canEditField.

Text the whole table reads — an action's chat message, a timed effect's name and description — is built from what a player who does not own the token sees. A field whose scope is not visibleTo: "all" never reaches it: a computed substitution with it ({8 + proficiency_bonus}) prints a dash, a plain {key} prints as written, and the action editor names such fields under the text. Hide a field only when the table must not know it; a value that follows from visible fields (D&D's proficiency bonus from level / CR) gains nothing from hiding.

9. Articles for fields and sections

A sheet field (a class, a race) and a section (features, inventory) can take their value or records from the compendium books linked to the room. The system says what a field takes; the book says where its articles are — by their tags. Tags are data an author edits; this query is the one place a system names them.

// field "class"
"articles": { "tags": [["Тип: Класс", "Type: Class"]] }
// field "subclass": a subclass of the class chosen in the field "class"
"articles": { "tags": [["Тип: Подкласс", "Type: Subclass"], ["Класс: {class}", "Class: {class}"]] }
  • tags — requirements, all of them must hold. A requirement is one tag or a list of equal alternatives (the same tag in several languages); an article meets it carrying any one. Tags compare exactly as the book wrote them.
  • {key} inside a tag stands for another field's value: every label and alias of its catalog entry (the sheet stores the id wizard, the book tags «Класс: Волшебник» or «Class: Wizard»), or the field's own text. An empty field drops the requirement — no class chosen, every subclass is offered. Every {…} must name another declared field ([a-z][a-z0-9_]*); the loader rejects any other. An alternative longer than 200 characters after the substitution is dropped; a requirement left with none is dropped as an empty field's is.
  • types (optional) — only these article types, at the top and among the rest. Omitted: a field takes every type a room member may search (Concept, Rule, Custom, Document, Object, Action, Condition, Effect); a section, its record type's article types — or every type, when the record type has none.
  • articles applies to text fields and entryList sections.

What a section's record holds. A section's query may say what a record taken from an article starts with:

// section "Заклинания" (entryList, entryType "spell")
"articles": {
  "types": ["Action"],
  "tags": [["Тип: Заклинание", "Type: Spell"], ["Класс: {class}", "Class: {class}"]],
  "fill": { "level": ["Круг: {value}", "Level: {value}"] },
  "set": { "prepared": true }
}
  • fill — a field of the record from the article's tags: every pattern matched whole against every tag (case and spaces as written) offers the text in place of {value}, and the first value that reads as the field counts («Круг: 12» does not fit a circle up to 9 — «Level: 3» after it does). A number field takes a decimal number within its min/max/integer, a flag true/false, an enum one of its options — by id or by an optionLabels label in any language and case, a tag-list the text as one item. None reads — the record keeps its own value from the article (an item's), else the field stays unset, not the convention's default: an article that names no circle is not of circle 1. In D&D an unset circle reads as 0 in prepared or level == 0: a spell whose circle the book does not name stays open, as a cantrip does, until the book is tagged.
  • set — values every record taken from an article starts with; each of its field's type (a number within its bounds, a flag, a text; an enum one of its options; not a tag-list) — the loader rejects any other.
  • The section's own seed (newEntry.data) wins over both and over an item's own values: a list filtered by a field keeps the record it takes. A value from a tag or from set wins over an item's own.
  • Both name fields of the section's record type (entryConventions); the loader rejects any other key, and a field's query takes neither.
  • An article that carries an action (Action) lends it through the record: the record gets the article's action as its own (usable, as an item's), and the sheet shows its button on the row and in the actions list. The token's own actions are not touched.

Articles that meet the query are listed first, under «Из компендиума»; any other article of the room's books follows under «Другие статьи», with its folder path. A book nobody tagged still fills the field — it is only not sorted. For a field the order is: the book's matching articles, the system's catalog, the rest.

What a pick stores. The field keeps a word: a picked article whose title is a catalog entry (by label or alias) stores that entry's id; any other stores the title as the field's own text (a world's «Артефактор»). A title with its name in another alphabet in brackets, «Волшебник [Wizard]», goes by the whole and by each name: it finds the entry by either, and as the field's own text («Артефактор [Artificer]») it meets «Класс: Артефактор» and «Class: Artificer» alike. A bracket in the same alphabet («Эльф [высший]») is part of one name. A source mark or a number in brackets — capitals only or no letters («Волшебник [PHB]», «Кольцо [+1]») — is dropped, and the name before it counts. Names that point at two entries name none — the field keeps the title. The link to the article lives beside the values in the engine key _fieldArticles as { [fieldKey]: { value, ref } } and holds only while the field still has that value: writing another value by any other path (an import, patch_state) drops the link by itself, and the same word written back brings it back. Do not write _fieldArticles by hand. Sheets without a sheetLayout (the flat legacy sheet) show a link but offer no picker. One who edits the sheet sees the value with a book that opens the article; one who only reads it sees the value as a link.

Tag vocabulary for D&D books

The built-in D&D 5e system asks (the 2024 edition, built on it, asks the same from its next publication):

  • class — «Тип: Класс» / «Type: Class»;
  • race — «Тип: Раса», «Тип: Вид» / «Type: Race», «Type: Species»;
  • background — «Тип: Предыстория» / «Type: Background»;
  • creature type — «Тип: Тип существа» / «Type: Creature Type»;
  • spells section — «Тип: Заклинание» / «Type: Spell» and «Класс: » (the character's spells first), the circle from «Круг: N» / «Level: N» (cantrips — «Круг: 0»); a spell taken from the book is prepared;
  • subclass — «Тип: Подкласс» / «Type: Subclass» and «Класс: » / «Class: », the class by a label or alias of the system's class catalog (the aliases carry the usual translations: «Клирик», «Чернокнижник», «Рейнджер», «Разбойник», «Боец»), or by the book's own name for a class the catalog has not («Артефактор»).

The axis «Тип» says what the article is; other axes say what it belongs to («Класс: Жрец» on a class feature). Keep the two apart: a class feature tagged «Класс: Жрец» is not a class. A book laid out in folders can be tagged by its folders in one pass — a rule «Классы › *» → «Тип: Класс» per kind of article.

11. Combat vocabulary and defaults

These optional blocks replace D&D assumptions in generic combat UI/runtime. They currently have no dedicated /systems page, so treat the JSON Schema and built-in manifests as the authoring source.

Abilities and save terminology

"abilities": [
  {
    "key": "reflex",
    "label": { "en": "Reflex" },
    "description": { "en": "Avoid sudden danger." },
    "saveFormula": "2d6 + reflex"
  }
],
"combatPresentation": {
  "save": {
    "label": { "en": "Resist" },
    "difficultyLabel": { "en": "Difficulty" }
  }
}

Without saveFormula, save resolution falls back to d20 + <ability>_mod. combatPresentation changes labels/help, not mechanics.

Critical-hit rule

"critRule": {
  "trigger": { "kind": "range", "min": 19, "die": 20 },
  "effect": { "kind": "double-dice" },
  "autoHit": "nat-max"
}

Trigger kinds: natMax, range. Effect kinds: double-dice, max-dice, add-max-total, multiplier, multiply-total, auto-hit, none. autoHit is orthogonal: nat-max makes only the natural maximum hit automatically; trigger makes every triggered critical hit. An action may override the system rule through actions[].crit.

max-dice adds only the maximum dice value; flat modifiers are counted once. add-max-total adds the maximum of the entire original damage formula, including constant modifiers: Dcrit = Drolled + Dmaximum. For example, 1d4+2 becomes 1d4+2+6 (a roll of 3 deals 11), and 1d4+2d6+3 becomes 1d4+2d6+3+19. Variables are resolved for the current damage roll before computing its maximum; the maximum adds no random dice. Use this mode for ordinary damage formulas: sums of dice plus numeric modifiers (including negative modifiers). The maximum is computed with maximum dice faces; arbitrary expressions with subtracted dice, rerolls or explosions are outside this mode's supported contract.

Set this once in the system manifest; actions inherit it unless they declare crit:

"critRule": {
  "trigger": { "kind": "natMax", "die": 20 },
  "effect": { "kind": "add-max-total" }
}

Rounding

"rounding": "floor"                       // one mode for everything
"rounding": {                             // or a map
  "default": "floor",
  "damage": "floor",                      // damage step totals, before saves and defenses
  "heal": "ceil",                         // additions to the engine health field `hp`
  "modifyField": "round",                 // every other modifyField value
  "resource": "floor",                    // consumeResource / restoreResource amounts
  "saveFactor": "floor",                  // the saver's share (saveRule.factor)
  "defenses": "floor"                     // each resistance / vulnerability stage
}

Modes: floor, ceil, round, none. Fractions come only from formulas ((1d8+4)/2 = 2.5); HP, fields and resources are integers, so the engine rounds every number that becomes state and every multiplier stage. The computation list is the engine's, not the system's. Absent → floor for everything. A step overrides its own computation through round on damage, modifyField, consumeResource, restoreResource and inside saveRule:

{ "type": "damage", "formula": "x / 3", "round": "floor" },
{ "type": "modifyField", "path": "hp", "op": "add", "value": "x / 3", "round": "ceil" }

Attack rolls and comparisons are never rounded: a fraction there is an authoring error for the editor diagnostics. floor(), ceil(), round() inside a formula still round an intermediate value; the flag owns the step's result. The card names the rounding in the value breakdown (2.5 → 2).

Initiative

"initiative": {
  "mode": "sorted",
  "rollFormula": "1d20 + initiative",
  "direction": "desc",
  "tiebreakers": ["dex_mod"],
  "stableFallback": "name"
}

sorted requires exactly one of rollFormula or sortKey. Other modes are narrative (hidePanel?) and manual (onRoundStart: preserve | master-prompt). If the block is absent, combat uses the legacy rolled fallback.

12. Item contributions, damage cascades, and state rules

These blocks move common combat/inventory policies out of hardcoded system handlers. They are optional; omitting them preserves the engine defaults.

Item rules

Each itemRules record evaluates against one item's own entry.data and contributes to an effective sheet field through the effects pipeline.

"itemRules": [
  {
    "id": "carried-weight",
    "label": { "en": "Carried weight" },
    "when": "equipped == 0",
    "key": "carried_weight",
    "mode": "add",
    "value": "weight"
  }
]

when is optional. Modes: add, multiply, replace-base, override, upgrade, downgrade. Both when and value see item fields, not character fields.

Damage cascades

"damageCascades": [
  {
    "id": "physical",
    "damageTypes": ["slashing", "piercing", "bludgeoning"],
    "pools": [
      { "path": "hp_temp" },
      { "path": "hp" }
    ]
  },
  {
    "id": "stress",
    "damageTypes": ["mental"],
    "pools": [{ "path": "stress", "signed": true }]
  }
]

The first matching typed cascade claims the damage; omit damageTypes for a catch-all. Intermediate absorbing pools stop at their declared numeric field min (zero when absent) and pass the remainder to the next pool. Terminal and signed pools use the declared min, or allow negative values when it is absent. The same field minima constrain combat field mutations and group HP controls. D&D declares hp.min: 0; this is not a global zero clamp.

Defense field bindings

"defenses": {
  "resistances": "damage_resistances",
  "immunities": "damage_immunities",
  "vulnerabilities": "damage_vulnerabilities",
  "conditionImmunities": "condition_immunities",
  "critImmunity": "crit_immune"
}

Each optional binding must name a declared field. Its catalog resolves IDs, localized labels and optional entry aliases (historical spellings). Combat reads effective values, including temporary effects. The built-in D&D system uses these bindings; other systems opt in explicitly. Resistance halves and rounds down, then vulnerability doubles; duplicate sources do not stack and immunity wins. A preceding save factor is applied before defenses. Legacy numeric resist_<type> fields remain supported. These bindings implement this specific defense model, not arbitrary user-defined multiplier rules.

critImmunity names a number field (sheet fields have no boolean, and sources add up): above zero, a critical hit against the creature is a normal hit — 5e Adamantine Armor. The attack still lands for every target (a natural 20 keeps its auto-hit), the dice are not transformed, and the card records a hit. Bare crit in a branch predicate still sees the trigger, so a hand-written atk >= target_ac or crit keeps hitting (and a hand-written when: 'crit' extra still fires). <capture>_crit respects immunity: inside a scope: "eachTarget" branch it answers for that target; outside, for the first target, as every branch predicate does — put crit extras for several targets in a per-target branch. Damage answers to each target: rollMode: perTarget per target; a shared roll with mixed targets rolls the crit dice for the others and a separate normal roll (own key, formula and dice on the target's row, rerolled there) for the immune ones (perTargetDamage[].baseTotal / .crit), and the combat card and outcome mark the crit per target. Immunity is read before the dice are rolled — a doubled roll cannot be taken back afterwards. The dice HUD still lights a natural 20: that is the die, not the outcome. An item grants it with an equip effect { "key": "crit_immune", "mode": "add", "value": 1 }.

State rules

State rules are re-evaluated after damage and healing. They can apply a declared condition and/or mark the actor defeated.

"stateRules": [
  {
    "id": "downed",
    "label": { "en": "Downed" },
    "when": "hp <= 0",
    "condition": "unconscious",
    "defeated": true
  }
]

A condition named by a rule is owned by the rules: it is applied while the predicate holds and removed when it stops holding. A rule that should also keep a condition applied by hand includes it in its own predicate (… || contains('active_conditions', 'dead')) — under the same numeric guard, so rolling back the hit that caused it (a rejected or corrected row) lifts it.

Besides the sheet's fields and derived fields, a rule reads one context variable, reserved over any field of the same name:

Variable Value
player_owned 1 when a player plays the token, else 0

A player plays a token when a user who is not the table's master owns it (ownerId) or holds the OWNER level in ownership, or when everyone does (ownership.default OWNER). The master's own token is not a player's; a player's token handed over through ownership alone is. The same answer decides the master's fog preview. (Who answers a roll or a save is another question — the account in ownerId.)

The rules are judged at one point: the master's client re-judges a token every time its data changes — damage and healing from any source (action steps, the sheet, the HP bar, the bridge's patch_state, undo, import), a status put on or taken off, an owner change — and every token of the table each time the master's client binds to the room (a load, a reconnect, a table switch, a rule-system swap), so data written while no master judged comes in line; only a difference is written. A rule-owned condition taken off by hand comes back while its predicate holds. A sheet the rules have nothing to judge on is not judged — neither for its statuses nor for the initiative order's «out of the fight»: rules that read hp judge only a sheet that has hit points (hp present and not a written 0 of 0 — a maximum or death saves alone do not count, an absent hp would read as 0); other rules judge a sheet that has any number they read.

It lets a system decide how a player's character and a creature leave the fight. D&D declares dying for a player's character at zero HP (hp <= 0 && player_owned == 1, defeated: false), and death — the standard dead condition, defeated: true — at zero HP for a creature, for a character after three failed death saves, or when dead is already on the token (applying dead by hand zeroes HP). Healing above zero lifts it. A system that keeps its creatures alive at zero simply does not test player_owned.

If no state rules are declared, the engine keeps its default defeated-at-zero HP rule. System-derived exclusions update when the state changes and are reconciled when reading initiative; explicit master exclusions remain manual. Historical defeated: true entries without provenance are preserved as manual.

13. Actions — generic flow primitives

Action steps form a sequence. Use captureAs to expose roll/save results, then branch to dispatch on predicates.

Action envelope

Besides required id, label, usableBy, and non-empty steps, an action may declare:

group, groupOrder Context-menu submenu and section order.
kind active, bonus, reactive-prompt, reactive-auto, or free; absent means active.
cost Resource-id → constant/formula map paid by the resolver.
repeat count and targetMode: same/rebound/distribute.
icon assetId or Lucide icon, optional color.

What a card shows of a spend

Whatever an action spent appears on its card as spend chips, at the end of the action line: the envelope (cost, or the turn of its kind), every consumeResource of the path the resolution took (a branch not taken spends nothing; resourceFrom shows the resource the answer chose), the item's charges, and the entry's uses. One resource spent by cost and by a step is one chip with the sum.

  • Who sees it. A player sees the chips of the tokens they play; the master sees all; the master in «Вид игрока» sees as that player. A resource whose current value dataScopes hide from the payer's own player is the master's secret: its spend is not written to the card at all (the master sees it on his waiting card, with the red crossed eye).
  • The chip. The kind's icon from resourceCategories (no kind — a gem), the resource's label (dropped when it equals the action's name — a potion spending itself), the amount «−1». The remainder «2/3» is read live from the sheet, only on the last card that spent that resource, only when the viewer may see the field and only when the maximum is under 10: big pools (arrows, gold) show «−1» alone.
  • States. Dashed — declared (the card waits for the master); quiet — spent; struck amount + the hammer, warning colour — the master applied it over a shortfall (nothing was taken); struck amount + the return arrow, green — returned on rejection; red remainder — short (a refusal, the choice window).
  • Turn marker. In combat, when the system names the turn kinds in resourceCategories: the action takes its turn slot by kind — action (green circle), bonus action (orange triangle), reaction (violet diamond) — or by an explicit cost of a turn resource; movement is yellow footprints.
  • Two chips, then «+N» — a press opens the row.
  • A refusal for a shortfall reads «Не хватает» with the chip of what is short and its red remainder; the chat line of a direct call carries the same sentence with the resource's name. An item spent by its action has no separate «использовал» line any more — the chip says it; «израсходован» and «превратился» stay.

Roll comparison and save projection

roll.compare turns a total into a hit/miss comparison without hardcoding AC:

{
  "type": "roll",
  "formula": "1d20 + attack_bonus",
  "captureAs": "attack",
  "tags": ["attack"],
  "compare": {
    "threshold": "target_ac",
    "op": "gte",
    "marginAs": "margin",
    "label": { "en": "Armor class" }
  }
}

Comparison ops: gte, gt, lte, lt, eq; default gte. An attack roll carries "tags": ["attack"]: a timed effect's rollModifier: {tag: "attack"} («disadvantage on the next attack») finds the bearer's roll by this tag only — never by compare or by the captureAs name ("attack" above is the result's name, not its tag). damage.saveRule and effect.saveRule project a preceding per-target save onto each target without rerolling a shared area result. from names the save's captureAs; omitted means the most recent save. factor: "0.5" halves damage for savers, while factor: "0" negates damage or an effect.

Reactions

A reaction listens at a closed resolver boundary and may prompt an owner, rerun from a phase, or cancel from that phase:

"reaction": {
  "trigger": { "phase": "preDamageApplication", "when": "hp <= 5" },
  "prompt": {
    "owner": "self",
    "label": { "en": "Use reaction?" },
    "timeoutSec": 15
  },
  "onAcceptCancel": "preDamageApplication"
}

Phase ids: preItemRoll, preambleComplete, preAttackRoll, preCheckHits, postAttackRoll, preSave, postSave, damageBonus, preDamageRoll, postDamageRoll, preDamageApplication, preActiveEffects.

Reading the source. A reaction's conditions (trigger.when, and when of its branches) read the action it answers through functions with a string argument:

"trigger": { "phase": "preItemRoll",
             "when": "is_caster == 0 and source_spent('spell_slot') > 0" }
  • source_spent('<kind>') — units of that kind (resources[].category) the source spent — its caster or the table — by the phase: the envelope cost, the steps of the path it took (resourceFrom included), the item's charges;
  • source_spent_rank('<kind>') — the highest rank among them, 0 if none;
  • source_spent_key('<key>') — by the resource key;
  • source_answer('<prompt id>') — the source's answer; a setup answer of a repeating action is given once and reads its value; a question answered more than once during the resolution (inside a repeat or «for each target») reads 0;
  • source_action('<id>'), source_entry_type('<entry type>') — 1 when the source is that action / was lent by a sheet record of that type.

A spend that comes before the first step with a phase (and the envelope) is declared — seen from preItemRoll; one after such a step is seen from the phase after it, so a slot spent only on a hit is not seen before the roll. is_target, is_caster, hit, attack_total, save_failed stay flat names. The functions are valid only in an action with a reaction block — elsewhere the loader refuses them; dice formulas (damage, rolls) do not know them — compare in a branch. source_cost_<key> still reads (now the sum by key of every path, so it sees cast_spell's slot too) but is deprecated: the loader warns, read source_spent_key('<key>') or source_spent('<kind>').

Cancel. onAcceptCancel: P in the quick flow spends what the source declared by P (the first P at or after the event that raised the reaction) — the envelope, the item's charges and the declared steps of its own price; a drain of its targets is what it does and is not applied, nor anything else; the source's card reads «Отменено: » with those spends and the reaction's row. A reaction that could not pay when answered (its price short) cancels nothing. A reaction the master adds to a card by hand answers no event: its source_* functions read 0. source_cost_<key> does not count the turn the source's kind takes; source_spent('action') and the other turn kinds do. On an interactive card the master decides; the card shows what was declared as dashed chips.

The reaction window shows its owner the source as the public card names it — «Культист · Огненный шар» with its spends by kind and rank (no remainder, never a master secret, nothing for a hidden source) — and «Ваша трата»: the reaction's own envelope and steps with the turn marker.

An action cannot contain an arbitrary hook step. Imperative escape hatches break serialisability, static permission inspection, and replay. Runtime operations deliberately exposed by the engine route through the typed capability registry. See the engine design notes (not published) §3.3 and §7.

Capability step

Invoke a registered capability by id. Capabilities are TypeScript handlers declared in the engine with typed Zod inputs/outputs and a declared effects set (pure | state-mutation | ui-notification | network | timer | random | admin). Loader checks:

  1. ref exists in the registry.
  2. args keys present in capability.inputs schema.
  3. action.usableBy: 'owner' cannot invoke capabilities with admin effect.
{
  "type": "capability",
  "ref": "combat-tracker.advance-turn",
  "args": { "combatId": "{combat_id}" },
  "captureAs": "turn_info"
}

Arguments are formula expressions resolved against caster vars + captures. The interpreter (production) invokes the handler async fire-and-forget; captured output binds via runtimeInputs[captureAs] for downstream steps. Authors do not register capabilities — that happens in core code; manifest only references by id.

D&D melee attack

{
  "id": "melee-attack",
  "label": { "en": "Melee Attack" },
  "usableBy": "owner",
  "targeting": { "shape": "single", "range": 1, "maxTargets": 1 },
  "steps": [
    { "type": "roll", "formula": "1d20 + str_mod + proficiency_bonus", "captureAs": "atk", "tags": ["attack"] },
    {
      "type": "branch",
      "cases": [
        {
          "when": "atk >= target_ac",
          "then": [
            { "type": "damage", "formula": "2d6 + str_mod", "damageType": "slashing" }
          ]
        }
      ]
    }
  ]
}

Predicate variables: caster's fields (flat: str_mod), target's fields prefixed with target_ (target_ac), and captures from preceding steps (atk here, saved for save-then-branch, result for PbtA 2d6+stat).

target_ covers every field and derived value of the first target, not only its defence: target_save_dex, target_skill_athletics_bonus, target_passive_perception — whatever the system's sheet declares. That is enough for a contest against a passive value: the roll 1d20 + skill_athletics_bonus with compare.threshold 10 + target_skill_acrobatics_bonus is a grapple resolved by the caster's dice alone. A threshold is deterministic (no dice), so a contest where the target also rolls is two steps today — the target's side goes through a save-style prompt — and not a single compare.

when uses the full deterministic expression language: arithmetic and parentheses (RAW + spell_attack_mod >= target_ac, (DONE - spell_attack_mod) == 20), comparisons, and boolean and/or (&&/|| aliases are accepted). A malformed expression fails closed and does not select the case.

Attack branches may declare an explicit outcome: "hit" | "miss". If one case declares it, every sibling case must do so. This separates control flow from the combat verdict: selecting a critical-failure or miss narration is no longer mistaken for a hit. Branches without outcomes remain valid for PbtA bands, resource routing, saves, and legacy stored actions.

"steps": [

Chat templates

chat.text is evaluated when that step resolves. Its scalar presentation scope contains:

  • action locals captured by preceding steps (roll.captureAs, save.captureAs, prompt.id, compare.marginAs, and crit);
  • source fields without a prefix ({hp}, {str_mod}, {ac});
  • first-target fields with target_ ({target_hp}, {target_dex_mod}, {target_ac});
  • {source_name}, {target_name}, and {target_count} pseudo-fields.

Captured locals win on a name collision. Actor values are effective values at the start of resolution (before this action applies its mutations), not a live post-damage read. They come from a separate non-owner presentation snapshot and are permission-filtered after effects and overrides are applied. Owner-only and master-only fields therefore stay unresolved instead of leaking from the master-authority mechanics context. Without a linked rule-system manifest only the name/count pseudo-fields are exposed, because there is no field visibility schema to evaluate.

The syntax is the unified template runtime used by other presentation fields:

"steps": [
  { "type": "roll", "formula": "1d20", "captureAs": "RAW", "tags": ["attack"] },
  {
    "type": "chat",
    "text": "{source_name} ({hp}/{hp_max}) attacks {target_name} ({target_hp}/{target_hp_max}, AC {target_ac}): {RAW}"
  },
  {
    "type": "chat",
    "text": {
      "en": "{if RAW == 20 then 'Critical hit' else 'Ordinary hit'} ({RAW})",
      "ru": "{if RAW == 20 then 'Критическое попадание' else 'Обычное попадание'} ({RAW})"
    }
  }
]
  • {RAW} substitutes a value.
  • {RAW + bonus} evaluates a pure expression when both captures exist.
  • {if condition then value else value} selects presentation text without changing action mechanics.
  • \{ and \} render literal braces.
  • An unknown variable stays visible ({RAWW}) instead of silently becoming zero, which makes chat useful for action debugging.

Only values known during synchronous action resolution are available. A real async capability result is not visible to a later chat unless the caller pre-binds it through runtimeInputs.

Typed mutation steps

Replacement vocabulary for the dropped hook step. Each step emits a typed mutation record; the effect interpreter applies it to live state and returns a structured step result.

// Consume a spell slot — fails the action if slot is empty.
{ "type": "consumeResource", "resourceId": "spell_slot_3", "amount": "1" }

// Restore HP fully on long rest.
{ "type": "restoreResource", "resourceId": "hp", "amount": "max" }

// Reduce target dex by 2 (clamped at 0).
{ "type": "modifyField", "path": "dex", "op": "add", "value": "-2",
  "target": "each" }

// Ask the player which slot to upcast — each option names the slot it
// spends; the choice window shows what is left of each.
{ "type": "prompt", "id": "slot_level", "kind": "select",
  "label": { "en": "Slot level" },
  "options": [
    { "value": 3, "label": { "en": "3rd" }, "resource": "spell_slot_3" },
    { "value": 4, "label": { "en": "4th" }, "resource": "spell_slot_4" },
    { "value": "pact_magic_level", "label": { "en": "Pact Magic" },
      "valueFrom": "field", "resource": "pact_magic" }
  ],
  "default": 3
}
// …and spend the chosen one: one step, not a branch per option.
{ "type": "consumeResource", "resourceFrom": "slot_level", "amount": "1" }

Semantics (codified in the engine design notes (not published) §5.3):

  • consumeResource with insufficient current → step fails, action aborts. Wrap in branch { when: 'resource > 0' } for soft-fail.
  • modifyField path must reference a declared field (load-time check) and the action's usableBy must satisfy the field's scope editableBy.
  • target: 'each' + downstream branch reading the same path → rejected at load (semantically incoherent for multi-target).
  • prompt is pre-flight: all prompts in an action's step tree are collected before any step runs.

Status overlay — how a status is drawn over the token

A status is shown on a token in two ways. The marker is its badge in the token's status row — always there unless hidden. The overlay is drawn over the token itself: code (HTML/SVG and <style>), the platform's «portrait» (desaturation, darkening, tint, transparency) and three flags. A status declares its overlay in the catalog; the room may switch it off, pick a preset or write its own (status settings, «Исполнение»; the bridge — see the engine design notes (not published), «Room settings»).

"conditions": [
  { "id": "dead", "...": "…", "overlay": { "preset": "death" } },
  {
    "id": "petrified", "...": "…",
    "overlay": {
      "html": "",
      "portrait": { "desaturate": 1, "tint": "#c2b08a", "tintAmount": 0.32 },
      "marker": "show",
      "priority": 80
    }
  },
  {
    "id": "burning", "...": "…",
    "overlay": {
      "html": "<div class=\"flames vtt-upright\">…</div><style>.flames { … }</style>",
      "portrait": { "tint": "#ff7a1a", "tintAmount": 0.32 },
      "priority": 40
    }
  }
]

overlay is either { "preset": "<id>" } (and nothing else) or a full definition — an object with html is a definition whatever else it carries:

Field Value Why the limit
html markup and <style>, up to 16 KB a hundred tokens parse it in every viewer's memory
portrait.desaturate 0…1 —
portrait.darken 0…0.85 darker, the portrait is not recognisable
portrait.tint + tintAmount #rgb/#rrggbb, 0…0.8 stronger, the portrait is a flat fill
portrait.opacity 0.2…1 fainter, the token is lost even to those who see it
marker show (default) / hide the marker while the overlay is drawn
evident true seen by players with the token's characteristics hidden
suppressOthers true overlays of less important statuses are not drawn
priority 0…100 order in the stack, the centre, the tint

Presets — data the platform ships, updated with it (changing a preset changes every system that names it): death (desaturate 1, darken 0.55, the status icon in the centre, marker hidden, evident, suppresses others, 100), unconscious (darken 0.2, icon in the centre, rising «z z z», marker hidden, evident, 90), poison (drops, green tint, 20), burning (flames, orange tint, 40), invisible (ripples, opacity 0.45, 30), web (a cobweb, 35), frost (frost, half desaturation, blue tint, 45), icon (the icon in the centre, marker hidden, 15).

The code's box and inputs. The code is drawn in a shadow root over the token: coordinates are the token's box (0…100 %), a 25 % margin around it is visible, beyond it is cut. It never catches the pointer (pointer-events is removed). Inputs are variables on the host: --token-size (px), --token-color, --status-color (colours only — anything else is empty), --status-stacks, --status-rounds (integers, 0 — none), --token-clip (the token's form as clip-path), --token-mask (the picture's alpha for a shapeless token), --tl-zoom (the table's zoom: a constant on-screen width is calc(2px / var(--tl-zoom))); host attributes data-shape, data-viewer (master/player), data-motion="reduce", data-lod="small". Placeholders, filled after cleaning in the code's TEXT only: {{icon}} (the status icon with a dark halo), {{icon:name}} (any Lucide icon), {{name}}, {{stacks}}, {{rounds}}. In an attribute or a <style> a placeholder stays as written — numbers reach CSS through var(--status-stacks) / var(--status-rounds). Platform classes: vtt-body (inside the token's form), vtt-center (the shared centre: one place 48 % of the side, two — 27 % each; a status that loses the centre gets its marker back), vtt-halo (an icon with a dark halo), vtt-upright (does not turn with the token's facing). Animate transform and opacity; on a small token and with «less motion» animations stand still.

What cleaning removes — at every viewer, at draw time, whoever wrote the code: scripts and event handlers; SMIL animation; foreignObject, frames, use, links, SVG image; pictures other than your own files and data:; an SVG fill, stroke, mask or clip-path that is not a plain colour (hex, rgb()/hsl()/oklch()… of numbers and units, a colour word, none), url(#id) of the same code with an optional fallback colour, or — for clip-path and mask — a basic shape (circle(), ellipse(), inset(), polygon()); a variable there goes too — set it in style (the browser reads these attributes as CSS, escapes included); addresses outside Rolebaza in styles, @import; position: fixed/sticky and :host; pointer-events and all; filter and backdrop-filter (re-run on every frame of an animation — use the portrait); code that keeps no element (a <style> alone draws nothing, and its status keeps its marker); over 200 elements or 16 KB — the whole code. An animation shorter than 0.34 s is lengthened to it (flashing more than three times a second is dangerous for photosensitive viewers); its length must be a number, not var()/calc(). Do not draw an outline of the token's form in code — the selection light and the turn ring are other layers.

Several statuses. Overlays stack, at most two layers of code; the most important one on top. A code overlay past the two is not drawn at all, its portrait neither; an overlay with no code (the portrait alone) takes no layer. If the most important drawn status suppresses others, it is drawn alone and their markers come back. Desaturation and darkening take the maximum, opacity the minimum, the tint is the most important one's. A marker leaves the row only while its overlay is drawn in full and the marker is hidden — a portrait-only overlay owns a channel only when it is the most important status setting the value shown, and keeps its marker unless it owns every channel it sets — so a status is never lost.

Who sees it. The overlay follows the status row's own ladder for the viewer: whoever does not see the row does not see the overlay; «evident» lifts only «characteristics hidden». «Скрыть подписи» puts overlays out for everyone. The initiative bar shows the portrait and the centre icon, not the free code. A token turns overlays off for itself in its status row («Оверлеи статусов на токене», status-cluster config.overlays: false).

The right to code. Writing or changing a full overlay definition in a system is the right of the Expert level (status.overlay.author): the server refuses the save (403, PLAN_FORBIDDEN, capabilityKey: "status.overlay.author") when code appears or changes. Presets, keeping code, editing anything else, removing code and cloning a system with code need no right.

Central marks. A status-to-token overlay that takes the centre replaces a central autoModifiers mark of the same meaning (D&D's skull): gate the mark with a predicate (contains('active_conditions','dead') == 0) rather than deleting its row — the ids of the rows after it would shift. D&D's dying moon is not drawn under «Без сознания» (… && contains('active_conditions','unconscious') == 0).

Порядок применения и конфликты

Изменения одного поля сортируются по приоритету режима (меньший — раньше):

база листа
  → custom 10 → replace-base 15 → multiply 20 → upgrade 25 → add 30
  → override 50 → downgrade 70
  • replace-base против add: замена идёт первой, прибавки ложатся сверху — латы «заменить 18» + щит «прибавить 2» = 20.
  • Несколько replace-base на одном поле: работает НАИБОЛЬШЕЕ вычисленное значение (как «надет лучший доспех»), порядок инвентаря не влияет; проигравший остаётся в разборе значения перечёркнутым с именем победителя. Ослабление («скорость становится 5») выражайте через downgrade — он режет итог последним и не соревнуется с заменами.
  • override бьёт всё, включая replace-base; вклады, которые он выбросил, в разборе перечёркнуты. Редактор предметов его не предлагает — он для состояний систем и особых эффектов.
  • Явный change.priority переопределяет умолчание режима точечно.
  • Legacy: записи предметов, сохранённые до раскола (mode override из прежнего «заменить»), читаются как replace-base в sanitizeChange / readEquipDraft и мигрируют при первом пересохранении.

Порядок вычисления полей — граф зависимостей

Формульные значения эффектов (11 + dex_mod) читают ЭФФЕКТИВНЫЕ значения полей, на которые ссылаются: конвейер строит граф зависимостей (узел — поле, ребро — имя в формуле) и вычисляет поля в топологическом порядке, как электронная таблица. Пояс «+4 к dex» доезжает до формулы доспеха через derived dex_mod на любой глубине цепочки. Правила:

  • самоссылка (формула эффекта на X читает X) — читает БАЗУ поля;
  • цикл между полями не решается по определению (язык тотален): участники считаются по пред-эффектному снапшоту детерминированно, а в EffectiveSystemData.warnings появляется { kind: 'cycle', fields }. Участник — каждое поле клубка взаимных ссылок (компонента сильной связности), а не только лежащие на одном пути: итог не зависит от порядка предметов при любом числе полей в цикле;
  • ручной оверрайд мастера пришпиливает поле: оно становится константой графа и разрывает цикл через себя;
  • скрытое от игрока поле в формулах игрока остаётся сырым (базовым) — эффективное значение скрытого не утекает.

Условие изменения when

2026-09-30. Любое изменение (у состояния, у предмета в «Пока надето», в шаге timedEffect, у эффекта токена) может нести when — условие по ЭФФЕКТИВНОМУ листу, которое перечитывается при каждом расчёте:

{ "key": "ac", "mode": "add", "value": 1, "when": "dex >= 14" }

Плащ даёт +1 КД, пока ловкость не меньше 14, — считая пояс ловкости и любые другие вклады в dex. Правила:

  • Порядок. Имена из условия — рёбра того же графа полей: dex вычисляется раньше ac, порядок предметов в инвентаре не важен. Самоссылка (ac >= 12 у изменения КД) читает БАЗУ поля.
  • Невыполненное изменение не участвует в расчёте поля вовсе — ни в стекинге категорий, ни в соревновании replace-base. В разборе значения оно стоит перечёркнутым в конце с пометкой «условие не выполнено» и с величиной, которую дало бы, если бы условие выполнилось (посчитанной той же свёрткой: проигравшая замена назовёт победителя).
  • Условие с ошибкой (синтаксис, неизвестная функция, нечисловой ответ вроде бесконечности) ничего не даёт, лист не роняет и помечается «условие записано с ошибкой» — не путается с честно ложным.
  • Пусто, пробелы или null — условия нет, изменение действует всегда. В манифесте пустой when — ошибка схемы: не пишите поле вовсе.
  • Поле, у которого все вклады выключены условиями, не считается изменённым: вместо акцентной точки разбора у него тихое полое кольцо, а разбор показывает выключенный бонус зачёркнутым с причиной.
  • Загрузчик отказывает на сломанном when и на неизвестных именах. У состояния ступень n в when запрещена (она только в predicate), у timedEffect запрещены захваты действия и table_*: условие читает лист позже, когда действия уже нет.

Три похожих поля — не одно и то же:

  • change.when — живое условие по листу (этот раздел);
  • change.predicate у состояния — ступень {n} градуированного состояния, вычисляется при наложении (см. «Graded conditions»). Слияние с when запланировано (the engine design notes (not published) §5.2);
  • itemRules[].when — условие по полям самого ПРЕДМЕТА (equipped, weight), не персонажа.

Состояние условия: выполнено / не выполнено / с ошибкой.

Одна семантика всех условий

С 2026-09-30 любое условие системы читается одинаково: when изменения, itemRules[].when и «пока надето, если…», predicate у чипов, модификаторов и видимости блоков, autoWhen вида листа, условия веток, полос результата и when шагов действий, trigger.when реакций, stateRules[].when, where разделов листа, requires[].when записей.

  • Пусто, пробелы, true — выполнено; false — нет.
  • Голое имя читает само значение: непустой список или текст, ненулевое число, true — выполнено; отсутствующее поле — нет.
  • Иначе — значение выражения: число ≠ 0 (отрицательное тоже), непустая строка, true.
  • Не вычисляется (синтаксис, неизвестная функция, бесконечность или NaN — из выражения или из поля по голому имени) — «записано с ошибкой»: не выполнено, а где есть место показать — показано.

Что делать с пустым и с ошибкой, решает место, где условие стоит, — и только это. Правило состояния с пустым when не срабатывает (правило не задано, а не «всегда»: иначе недописанное «повержен» валило бы любое существо). Раздел листа с нечитаемым where запись не прячет. Требование записи без формулы или с нечитаемой формулой — «не проверено».

Что это изменило (по данным прода — одно действие одного токена):

  • пустое или из пробелов условие ветки, полосы результата, when шага раньше не срабатывало никогда, теперь срабатывает всегда: пустая последняя ветка — это «иначе»;
  • правила предметов, правила состояния и where: отрицательное число и непустая строка раньше были «ложью», теперь «истина»;
  • голое имя списка или объекта в ветке, реакции, правиле предмета раньше читалось как 0, теперь «непустой — истина»;
  • NaN и бесконечность раньше считались «истиной», теперь «записано с ошибкой»;
  • predicate из одних цифр (1) раньше читал поле с таким именем («ложь»), теперь — число. Пишите true явно: загрузчик пустое условие не пропускает, но в действиях токенов оно встречается. Единственное отличие predicate: слово справа от сравнения, которого нет среди полей, читается как строка (race == elf).

Graded conditions (numericValue)

Conditions that scale (Exhaustion 1-6, Frightened N) use predicate-gated changes + severityTiers ladder.

{
  "id": "exhaustion",
  "name": { "en": "Exhaustion" },
  "icon": "battery-warning",
  "polarity": "debuff",
  "hasNumericValue": true,
  "changes": [
    { "key": "flags", "mode": "set-flag", "value": "disadvantage_ability_checks", "predicate": "n >= 1" },
    { "key": "speed", "mode": "multiply", "value": 0.5, "predicate": "n >= 2" },
    { "key": "flags", "mode": "set-flag", "value": "disadvantage_attacks", "predicate": "n >= 3" },
    { "key": "hp_max","mode": "multiply", "value": 0.5, "predicate": "n >= 4" },
    { "key": "speed", "mode": "override", "value": 0, "predicate": "n >= 5" }
  ],
  "severityTiers": [
    { "threshold": 5, "severity": "severe" },
    { "threshold": 3, "severity": "warn" },
    { "threshold": 0, "severity": "none" }
  ],
  "statuses": ["exhaustion"]
}
  • predicate evaluates against {n: numericValue}. Changes without a predicate always apply.
  • severityTiers highest-threshold-first; first match wins. Explicitly cover all reachable values (don't forget the low tier).

Stacking conditions (stacks)

A condition that piles up — poison from several bites, bleeding — declares stacks: true (no limit) or { "max": 5 }. Applying it again adds a stack to the one effect on the token instead of replacing it; the stacks are the same N a graded condition carries, so changes read them through {N} and predicates through n.

{
  "id": "poisoned",
  "name": { "en": "Poisoned", "ru": "Отравлен" },
  "icon": "droplet",
  "polarity": "debuff",
  "stacks": { "max": 5 },
  "changes": [
    { "key": "attack_bonus", "mode": "add", "value": "-{N}" },
    { "key": "speed", "mode": "add", "value": -10, "predicate": "n >= 3" }
  ],
  "statuses": ["poisoned"]
}
  • One effect per condition on a token, whatever applies it: two casters' poison is one poison with more stacks.
  • The first application gives addStacks stacks (default 1); each next one adds that many, up to max. The duration restarts on each application unless the step says refreshDuration: false (see effect and timedEffect in the DSL reference).
  • Switching the condition on by hand or by a state rule does not add stacks; the master changes the count on the token (the number on the badge, shown from two stacks; the statuses panel; the token menu).
  • A whileEffect application (bound to a source effect) keeps its own effect and does not stack; a captureAs instance adds to the status like any other application, and its whileEffect dependents follow the merged effect.
  • n in a predicate is the condition's: its changes are re-derived for the count. A timedEffect reads stacks through {N} only.
  • {N} also reaches the condition's own round actions: "{N}d4" on three stacks rolls 3d4.
  • Absent or false — re-applying replaces the effect, as before.

16. Sheet layout

Declarative tree of layout nodes. Replaces legacy sheetHTML string. Node types: tabs / fieldGroup / pairedFieldGrid / resourceBar / row / col / heading / divider / html / collapsible / entryList / traitsList / actionsList / effectsList / portrait / progressBar / restControls / resourceList / conditionsList / equipmentSlots. The html node is a deprecated escape hatch; prefer typed nodes for data-bearing content.

visibleIf — a node only while a condition holds

Every layout node accepts "visibleIf": a condition in the sheet's expression language (the language of derived fields) over the character's sheet data.

{ "type": "resourceBar", "resourceKey": "laying_hands", "presentation": "compact", "visibleIf": "laying_hands_max > 0" }
{ "type": "collapsible", "title": { "ru": "Заклинания" }, "visibleIf": "level_bard + level_druid > 0", "children": [ ... ] }
  • Not met — the node is gone for every viewer, the master included. It leaves its container, so no gap stays behind; a collapsible, row or col whose children are all hidden goes too (an authored empty one stays). An item of tabs has no visibleIf — hide its content instead.
  • Each viewer's own data decides: a field or derived value the viewer may not see (dataScopes) reads as 0 for them, and has_entry sees only the entries they see — so a node can show for the master and not for a player.
  • A condition that does not evaluate, or names something the sheet does not have (a typo in a field name), shows the node rather than hiding it. Both are reported at load: syntax by the formula stage, an unknown name by the scope stage with a suggestion, at path …layout.….visibleIf — in sheetLayout, sheetVariants and table.layout (the table's sheet reads the table's own fields).
  • A bare name reads the value itself: "visibleIf": "level_paladin" holds while it is non-zero. Names are the sheet's data: fields, the stored values of resources (laying_hands_max — not the resource's own id), status-track counts (health_agg) and derived values; has_entry('slug') reads the sheet's entries taken from a compendium (the table's sheet has none). Action-time names (target_*, captures) do not exist on a sheet. A field name given as text (contains('field', …), sum_matching('prefix')) is not checked — a typo there reads as nothing.
  • It decides presentation only: hidden fields keep their values, actions and formulas still read them.

entryList — a section whose length belongs to the character

Renders the token's records of one ListEntryType. Use it wherever the SET of things is the character's own rather than the system's: Fate skills, stunts, aspects and consequences; anything a player should be able to add with +.

{ "type": "entryList", "entryType": "ability",
  "presentation": { "kind": "grid" },
  "title": { "en": "Skills" },
  "newEntry": { "data": { "value": 0 } } },

{ "type": "entryList", "entryType": "condition", "tag": "aspect",
  "title": { "en": "Aspects" },
  "newEntry": { "tags": ["aspect"] } },

{ "type": "entryList", "entryType": "condition", "tag": "consequence",
  "title": { "en": "Consequences" },
  "newEntry": { "tags": ["consequence"], "data": { "severity": "mild" } } }
  • tag narrows the section to records carrying that tag, so several sections can share one record type. Reach for it before asking for a new ListEntryType: the vocabulary is closed, and two lists that differ only by taxonomy are what tags is for. An untagged section still shows tagged records — a tag narrows a section, it does not carve the record out of its type.
  • newEntry seeds what this section's + creates: tags (required when tag is set — the loader rejects the manifest otherwise, since new rows would fail their own filter) and data defaults layered over the convention's own default values.
  • presentation is the semantic renderer choice: { "kind": "list" } (the default for every existing manifest), { "kind": "grid" } for a compact responsive set such as Fate skills, or { "kind": "resources" } for editable personal counters (only with entryType: "resource"). The manifest does not declare columns, breakpoints or pixels; the shared renderer owns geometry and falls back to one column when the panel is narrow.

Rows get a roll button when the record or its convention declares a roll — see Entry conventions → roll.

articles (optional) names the compendium articles this section's + offers first — the same query as a field's, see Articles for fields and sections; {key} reads the stored values of the sheet. A section of any record type may declare it. Without it only two record types take articles: features list concepts, rules and custom articles first, the inventory objects first, and other types below. A picked article becomes a record of the section with the article's text — an Action or Condition article gives its text, not its mechanics. A catalogue: true section offers its own declared records, and a resources section has no + to offer from: neither takes articles (the loader rejects it).

Personal resources and inline field icons (2026-09-16)

{ "type": "entryList", "entryType": "resource", "presentation": { "kind": "resources" } } uses the existing per-character entries, not a second resource store. The master creates/configures the name, maximum and recharge; the owner can edit the current amount. newEntry tags/data and convention defaults still apply. Old resource entries are not guessed or silently converted: the master configures their counter.

The record stores data.resourceKey (generated personal_ + 32 UUID hex digits), current, max, and recharge (manual, short-rest, long-rest, dawn). entry-resources.ts projects it into the ordinary ResourceDef catalog and two transient field names. Those fields are never persisted in token systemData. The action editor reads the explicit character subject's visible entries; its resource options show names, preserving keys through rename and reorder. Envelope costs, consume/restore steps and rest use the common resource contract; the world adapter redirects writes back to the entry. Group rest reads each recipient's catalog. Deleted personal references fail payment, rather than becoming free actions or orphan fields. Undo restores existing counters without resurrecting deleted entries. Copying a character copies its entries and references together; values remain scoped to that character. Arbitrary imported actions do not create missing personal resources.

Fields may declare icon (Lucide name) and iconColor (six-digit hex semantic color). fieldGroup with presentation: "summary" displays a full label, icon, inline number and the field's description tooltip. D&D currency uses this for coin metals and exchange rates; it wraps on narrow sheets instead of scrolling.

The built-in D&D sheet places spellcasting settings above slots in one fold, retaining the slots section's stable ID. This changes presentation only: additional class-specific casting configurations or pact-magic pools are not inferred.

pairedFieldGrid — two related fields as one compact cell

Use this when two independently declared fields are read together in play. The primary field supplies the cell title and main value; both fields keep their own derivedKey, rollFormula, edit permission, and provenance hint. dot-track secondary fields render as an inline toggle. The grid wraps by its actual container width; minCellWidth (72–360, default 96) controls when. Each pair may override label / secondaryLabel for presentation without changing the referenced fields' data identity.

{
  "type": "pairedFieldGrid",
  "secondaryLabel": { "en": "save", "ru": "спас." },
  "minCellWidth": 88,
  "pairs": [
    { "primaryKey": "str", "secondaryKey": "save_str_prof" },
    { "primaryKey": "dex", "secondaryKey": "save_dex_prof" }
  ]
}

Pairing is explicit rather than positional: reordering either source fieldGroup cannot silently connect the wrong fields. Existing grid-3 / grid-6 field groups remain available when the values should stay separate.

collapsible — folds children behind a clickable title bar

Wrap any sub-tree to hide it behind a title bar until the user opens it. Pair with a stable id so the renderer persists open/closed state to localStorage across reloads. defaultOpen (default true) sets the initial state when no preference is stored.

{
  "type": "collapsible",
  "id": "combat-section",
  "title": { "en": "Combat", "ru": "Бой" },
  "defaultOpen": false,
  "children": [
    { "type": "fieldGroup", "groupId": "combat" },
    { "type": "resourceBar", "resourceKey": "hp" }
  ]
}

"sheetLayout": {
  "type": "tabs",
  "tabs": [
    {
      "id": "stats",
      "label": { "en": "Stats" },
      "children": [
        { "type": "fieldGroup", "groupId": "abilities" },
        {
          "type": "row",
          "children": [
            { "type": "fieldGroup", "groupId": "saves" },
            { "type": "fieldGroup", "groupId": "combat" }
          ],
          "gap": 8
        },
        { "type": "resourceBar", "resourceKey": "hp" }
      ]
    }
  ]
}

row из группы и полосы раскладывается сеткой

Строка ровно с двумя детьми, где первый — fieldGroup с label-inline или value-inline (и без presentation), а второй — progressBar, resourceBar или такая же группа, рисуется не флексом, а сеткой в 4 колонки (в узком контейнере — в 3, полоса занимает всю строку). Ячейки первой группы при этом становятся прямыми элементами сетки через display: contents, поэтому вложенные контейнеры внутри такой строки теряют свою рамку вместе с собственным gap. На этом правиле стоят листы D&D 5e SRD: там ряды «группа + полоса» выравниваются по колонкам между строками.

Если строка нужна обычной, распознавание отключается явно:

{
  "type": "row",
  "presentation": "plain",
  "gap": 10,
  "children": [
    { "type": "fieldGroup", "groupId": "defense", "layoutOverride": "value-inline" },
    { "type": "col", "gap": 4, "children": [ /* свой отступ здесь работает */ ] }
  ]
}

gap есть только у row и col; у остальных узлов отступами управляет сама раскладка. Чтобы задать расстояние между детьми, оберните их в row/col — и помните про распознавание выше, иначе обёртка исчезнет.

When sheetLayout is absent, the engine generates a default layout from fieldGroups ordering.

In the system editor, this optional top-level value is the singleton Fallback sheet record on the Sheets page. It deliberately shares the page with sheetVariants: both use the same layout DSL, while the fallback is consulted only after variant resolution fails.

sheetHTML and sheetTemplate remain accepted for old systems. New systems should use sheetLayout/sheetVariants: typed nodes participate in reference validation, permissions, responsive composition, and editor tooling, while legacy markup cannot provide the same guarantees.

List, portrait, progress, and dashboard nodes

Four declarative replacements for the deprecated html escape hatch:

// Actions tab — invocable buttons filtered by usableBy + viewer role.
{ "type": "actionsList", "usableBy": "owner",
  "title": { "en": "Actions" },
  "emptyHint": { "en": "No actions available" } }

// Active effects with optional dismiss button.
{ "type": "effectsList", "showDismiss": true,
  "title": { "en": "Active effects" } }

// Image slot. imageKey defaults to 'portrait'; fallbackKey kicks in
// when primary is absent. If both fields are empty, a token sheet uses the
// token's current image. aspect: 'square' | 'portrait' | 'landscape'.
{ "type": "portrait", "imageKey": "portrait", "aspect": "portrait" }

// Generic value/max bar for non-resource counters (XP, ammo, …).
// For declared resources prefer resourceBar — it resolves through
// ResourceDef.{current,max,temp}Key.
{ "type": "progressBar", "valueKey": "xp", "maxKey": "xp_max",
  "label": { "en": "XP" }, "color": "#a78bfa" }

reference-stage validates progressBar.{valueKey,maxKey} and portrait.{imageKey,fallbackKey} against declared fieldGroups keys. actionsList reads manifest.actions filtered by usableBy and current viewer role; built-in dnd5e-srd renders all 6 declarative D&D actions (rest / death-save / initiative / inspiration / cast-spell) through this node.

actionsList, effectsList and conditionsList accept "hideTitle": true when an enclosing collapsible, tab or heading already owns the visible section name. effectsList also accepts "hideWhenEmpty": true: use it for a technical sub-list inside a broader section so an empty pipeline does not create a second unexplained plate. These flags affect presentation only; stored actions, conditions and effects remain separate data domains.

The dashboard nodes use existing manifest data rather than introducing new storage:

  • restControls renders buttons for action ids in restIds;
  • resourceList renders declared resources and may filter by recharge or omit ids through exclude. With presentation (rows / grid) a resource whose maximum is 0 is not shown as a row; whoever may edit that maximum (the master, the owner) can bring it back with «+ Добавить» when the list names its resources in include. "hideWhenEmpty": true concerns the whole list, never single rows: when no row is shown, a list that is the content of a movable section (col with sectionsId) takes its section with it; elsewhere the list stays while its editor can still add a resource with «+ Добавить». To hide a list, a bar or a section by the character's data, use visibleIf;
  • conditionsList toggles ids from conditions in activeKey (default active_conditions);
  • equipmentSlots renders occupancy computed from equipment and item entries.

17. Sheet variants

sheetVariants declares parallel layouts for the same system. Each record has a stable id, an I18nLabel, and a required layout using the same tree as sheetLayout. The master can select a variant explicitly for a token.

"sheetVariants": [
  {
    "id": "vehicle",
    "label": { "en": "Vehicle", "ru": "Транспорт" },
    "autoWhen": "sheet_kind == 'vehicle'",
    "defaultFor": "manual",
    "layout": { "type": "col", "children": [] }
  }
]

Resolution order is deterministic: a known explicit token selection, then the first matching autoWhen, then the first matching defaultFor (player or creature), then the legacy sheet fallback. manual is never selected by ownership. Predicates read effective base + derived token data and use the shared predicate language; dice, loops, I/O, and plugin calls are unavailable.

Treat variant ids as durable references. Renaming or deleting one can leave existing tokens pointing at the old id; the editor warns about this but cannot count references across every room.

The Sheets authoring page owns both sheetVariants and the optional top-level sheetLayout. The latter appears as one removable, non-duplicable fallback record rather than as a separate document.

18. Vision catalogs

The optional vision block defines system-level vocabulary used by token and fog controls:

  • senses — darkvision, blindsight, tremorsense, and similar capabilities;
  • profiles — selectable token presets combining sight cones and senses;
  • fogProfiles — ambient light, range caps, and region modifiers;
  • modifiers — declarative changes to range or visibility tier;
  • defaultGroups — automatic observer-group membership;
  • rangeUnit and defaultProfileId — section defaults;
  • rangeOrigin — edge (default: range counts from the cells the token stands on) or center (from the token centre); the room and a fog zone may override it.
"vision": {
  "rangeUnit": "feet",
  "senses": [
    { "id": "hearing", "label": { "en": "Hearing" }, "mode": "sense" }
  ],
  "profiles": [
    {
      "id": "blind-hearing",
      "label": { "en": "Blind · hearing 60 ft" },
      "cones": [],
      "senses": [{ "ref": "hearing", "range": 60 }]
    }
  ],
  "defaultProfileId": "blind-hearing"
}

cones: [] explicitly means a sense-only profile: it receives no normal sight from the scene or zone. A sense with mode: "sense" ignores light and walls; mode: "see" still requires line of sight and illumination. Per-record rangeUnit overrides the section default. If a token references a removed or renamed profile, resolution uses a valid defaultProfileId before the engine fallback.

19. Distance method

distanceMethod supplies the system default when the room/grid does not override it:

  • chebyshev — diagonal and orthogonal cell steps cost the same;
  • alternating — alternating diagonal cost;
  • euclidean — straight-line distance;
  • manhattan — orthogonal sum;
  • hex — hex-grid distance.

Hex grids always use hex. Action and vision distances declared in feet are converted using the room grid's units-per-cell; cells stays engine-native.

20. Entry conventions

Declares the entry.data shape per ListEntryType so renderers surface compact chips, toggles, indicators, and detail fields without per-system TypeScript. The renderer maps each field's displayAs hint to a widget.

"entryConventions": {
  "item": {
    "label": { "en": "Items" },
    "fields": [
      { "key": "weight",        "type": "number",  "label": { "en": "Weight" }, "displayAs": "chip", "unit": { "en": "lb" }, "min": 0, "default": 0 },
      { "key": "equipped",      "type": "boolean", "label": { "en": "Equipped" }, "displayAs": "toggle-icon", "icon": "shirt" },
      { "key": "attuned",       "type": "boolean", "label": { "en": "Attuned" }, "displayAs": "toggle-icon", "icon": "sparkles" },
      { "key": "item_category", "type": "enum",    "label": { "en": "Category" }, "displayAs": "chip", "options": ["weapon", "armor", "gear", "tool", "consumable"] },
      { "key": "damage_roll",   "type": "formula", "label": { "en": "Damage" }, "formulaHint": "1d8+str_mod" }
    ]
  },
  "spell": {
    "fields": [
      { "key": "level",         "type": "number",  "label": { "en": "Level" }, "displayAs": "chip", "prefix": { "en": "Lvl" }, "zeroLabel": { "en": "Cantrip" }, "min": 0, "max": 9 },
      { "key": "school",        "type": "enum",    "label": { "en": "School" }, "options": ["abjuration", "conjuration", "divination", "enchantment", "evocation", "illusion", "necromancy", "transmutation"] },
      { "key": "concentration", "type": "boolean", "label": { "en": "Concentration" }, "displayAs": "toggle-icon", "icon": "brain" }
    ]
  }
}

Field types: number | text | textarea | boolean | enum | formula | duration | tag-list (closed).

DisplayHint: chip | toggle-icon | flag-when-on | inline-edit | details-only | hidden (closed). chip accepts localized unit, prefix, and zeroLabel; enum fields accept options and localized optionLabels. Number fields may declare integer: true; min, max and integer are validated before a widget commits a new value. Existing out-of-range stored values remain readable and are never rewritten merely by opening the sheet.

dimsRow — set on ONE boolean field per convention to make the whole row render at lowered contrast while the value is true. Use it for "spent this scene" states (a Fate stunt, an invoked aspect): the row is the thing the table scans, so the row is what has to look spent. Without it players fall back to typing (USED) into the name.

lendsActionsWhen — when a record of the type lends its actions (usable: an item's, or a spell's taken from a book) to its owner: a condition over the record's fields.

"spell": {
  "lendsActionsWhen": "prepared or level == 0",
  "actionGroup": { "id": "spells", "orderBy": "level" },
  "fields": [ /* level, prepared, … */ ]
}

While it holds, the record's actions are in the sheet's actions list, on its row and in the token menu; while it does not (or does not evaluate), they are not, and the row is dimmed. Absent — the record always lends. Compare with ==: a lone = does not parse, and the loader rejects the condition; every name in it must be a field of the type (a typo would read as 0). A gated record's actions are not dragged out: a copy on a screen button or a dice slot would keep working after the gate closes. actionGroup — the token menu's group (actionGroups[].id) for those actions, sectioned by the record's field orderBy (a spell by its circle; zeroSectionLabel names circle 0). The loader rejects an undeclared group and a field the type does not have. A lent action that changes nothing of its record runs at once like the token's own; one that spends its charges or transforms it (onInvoke.transformTo) goes past the master.

roll — a roll rule for the whole type, so a record added by hand is rollable without the player authoring a formula:

"ability": {
  "label": { "en": "Skills", "ru": "Навыки" },
  "fields": [
    { "key": "value", "type": "number", "label": { "en": "Rating" }, "displayAs": "inline-edit", "default": 0 }
  ],
  "roll": { "formula": "4dF + value", "label": { "en": "{name}" } }
}

Precedence is specificity, not novelty: a record's own hooks.roll (written by statblock import) wins; otherwise the type rule applies. The formula resolves against systemData + derived + the record's own data, with the record layered LAST — so value means "this record's value" even when the system declares a field of the same name. {name} in the label expands to the record's name.

Field key: must match the same snake_case DataKey regex used by fieldGroups[*].fields[*].key.

Convention is advisory, not enforced: entries can carry extra data fields not in the convention (forward-compat for homebrew). Undeclared keys render as raw key/value in details.

Compatibility for versionless entry data

ListEntry.data predates per-entry version markers. A convention may declare a narrow scalar compatibility projection instead of hard-coding a system id in React:

"legacyValueMaps": [{
  "sourceKey": "refresh",
  "cases": {
    "fate-point": {
      "setIfMissing": { "fate_point_cost": 1 },
      "unsetSource": true
    }
  }
}]

The projection is read-only until the user edits a convention field. At that point the same sparse entry command writes the projected target and removes the consumed source. Explicit canonical values win. The loader rejects unknown targets, duplicate source rules, competing target writers and values that do not satisfy the target field's type/options/range. This mechanism deliberately does not support formulas or arbitrary predicates; a second complex case is a signal to design versioned entry migrations.

21. Equipment slots

equipment declares where items can be equipped. It connects item entry data, the equipmentSlots layout node, and occupancy checks.

"equipment": {
  "slotField": "slot_id",
  "equippedField": "equipped",
  "slots": [
    {
      "id": "main_hand",
      "label": { "en": "Main hand" },
      "capacity": 1,
      "accepts": ["weapon"],
      "doll": { "x": 0.2, "y": 0.55, "side": "left" }
    },
    {
      "id": "wings",
      "label": { "en": "Wings" },
      "when": "has_wings != 0"
    }
  ]
}

slotField is the key in item entry.data that stores a slot id. equippedField defaults to equipped. accepts lists item-category values; when sees effective sheet data. doll coordinates are accepted metadata, normalized to 0..1; the current generic equipmentSlots renderer does not draw a character doll. This block is not related to root slotLists, which only positions token HUD badges.

22. Порядок результатов кубиков

Корневой ключ diceResultOrder управляет порядком вывода выпавших значений в чате, центральной плашке броска и разборе значений боевой карточки:

"diceResultOrder": "desc"
  • "desc" — по убыванию; умолчание, если ключ отсутствует.
  • "asc" — по возрастанию.
  • "none" — сохранять порядок, полученный от парсера.

Метки критов, успехов и отброшенных костей перемещаются вместе с числом. В групповых бросках перемещается весь подписанный результат группы; в пояснении со смешанными типами костей сортировка идёт внутри каждого отдельного блока типа. Для преимущества два набора остаются раздельными. Явная сортировка в формуле (6d6sa, 6d6sd, также 6d6s) имеет приоритет: если она присутствует, вывод всей формулы сохраняет порядок парсера.

Настройка применяется при отображении, в том числе к уже записанным броскам. Она не меняет сумму, выбор keep/drop, сохранённые rolls, diceMeta, индексы критов или план 3D-анимации. Это поле системы правил, не ActionDef.

23. Панель кубов

Панель собирается из манифеста. Ключа нет вовсе — работает умолчание движка (d4…d100, количества 1…6, преимущество и взрыв), поэтому у системы, которой хватает обычных костей, здесь пусто.

"dicePanel": {
  "rows": [
    { "id": "duality", "formula": "2d12", "glyph": "⬡",
      "label": { "ru": "Двойственные", "en": "Duality" } },
    { "id": "d6",  "die": "d6" },
    { "id": "d12", "die": "d12", "quantities": [1, 2, 3, 4] }
  ],
  "modifiers": [
    { "kind": "advantage" },
    { "kind": "explode" },
    { "kind": "term", "id": "hope", "formula": "+1d6",
      "label": { "ru": "Надежда +d6", "en": "Hope +d6" } }
  ],
  "shortcuts": [
    { "id": "init", "formula": "1d20", "icon": "hourglass", "color": "#475569",
      "label": { "ru": "Инициатива", "en": "Initiative" } }
  ]
}

rows — что показывает панель

Поле Ряд с костью Ряд с формулой
id обязателен, уникален в панели то же
die d4, d20, d100, dF, d% —
formula — любая формула из костей и чисел
label берётся из die обязателен
quantities быстрые количества, по умолчанию [1,2,3,4,5,6] неприменимо
glyph — знак на кнопке, один-два символа

Ряд с костью даёт кнопку, быстрые количества и счётчик. Ряд с формулой даёт одну широкую кнопку: количество к двойственным костям и к d616 неприменимо.

Поля «показывать счётчик» нет. Он есть у каждого ряда с костью и отсутствует у ряда с формулой; настройка, которая всегда равна одному и тому же, — это не настройка, а лишний способ ошибиться.

Кости судьбы в умолчании нет: её кидают системы семейства Fate, и они объявляют ряд сами — рядом с формулой ("formula": "4dF") или костью ("die": "dF"). За столом с обычными костями ряд «Fudge» ничего не делает и сбивает. Где кость судьбы объявлена, подсказка кнопки объясняет её сама: грани −1, 0 и +1 и размах итога по количеству костей.

Монета ("die": "dC"), наоборот, стоит в умолчании последним рядом: «орёл или решка» бросают за любым столом. Это честная двусторонняя кость с гранями 0 и 1, поэтому 3dC даёт от нуля до трёх. В формулах она пишется dC; строчное dc принимается только с количеством впереди, потому что голое dc — это переменная сложности с листа. Подсказку кнопки монета тоже носит свою, а на столе падает чеканной монетой с цифрой выпавшей стороны.

Сколько быстрых чисел увидит игрок, решает не только quantities. Ячейка числа имеет минимум и максимум ширины: на широкой панели ряд не растягивается гармошкой, на узкой числа не сжимаются в палочки — вместо этого их становится меньше, начиная с самых больших. Объявляйте quantities так, чтобы первые числа были самыми нужными: именно они переживут узкую панель.

Начального значения у счётчика тоже нет: в покое он показывает ноль, то есть «ряда нет в наборе», и туда же возвращается после броска. Ряд, добавленный кнопкой кости, получает одну кость.

Ряда константы в манифесте тоже нет: он есть всегда и берёт ровно те колонки, что количества костей. Константа — свойство броска, а не системы.

modifiers — переключатели над набором

  • advantage — пара «преимущество / помеха» на существующем двойном броске;
  • explode — взрывные кости (постфикс !);
  • term — своё слагаемое к формуле: { kind, id, label, formula }. Знак входит в запись (+1d6, -2); без знака читается как плюс. Состояние живёт в наборе панели и расходуется броском вместе с костями; хук не нужен. Переключатель влияет на бросок из панели, а не на бросок с листа персонажа.

advantage и explode — по одному на панель: два одинаковых переключателя означали бы два состояния одной настройки.

Умолчания у ключей независимые. Объявили rows — переключатели остались прежними (преимущество и взрыв). Чтобы убрать их совсем, напишите пустой массив: "modifiers": []. Так у Fate.

shortcuts — стартовая раскладка быстрого вызова

Чипы раскладываются по свободным слотам при первом входе игрока и дальше принадлежат ему: он их двигает и убирает. Слотов десять, поэтому и чипов не больше десяти. icon — kebab-имя Lucide, color — hex.

Что проверяется при загрузке системы

Формулы панели разбирает настоящий парсер кубов в момент загрузки, а не при нажатии: иначе опечатка доживает до первого броска и выглядит как сломанная кнопка, а не как ошибка манифеста.

  • формула обязана разбираться (2d6 + отклоняется);
  • переменные листа запрещены: 1d20 + str_mod отклоняется. У панели нет токена, подставлять их не из чего — такому место в действии персонажа;
  • d[имя] обязано ссылаться на объявленный diceTypes;
  • на именованный терм нельзя вешать модификаторы броска (d[marvel]!).

hidden — панель не нужна этой системе

"dicePanel": { "hidden": true }

Гаснут кнопка кубов в доке мастера и слот «Кубы» у игрока. Виджет «Кубы» на странице живых виджетов не гаснет: у него нет ни стола, ни системы.

26. Imperative hook references (deprecated)

Deprecated. No built-in system uses this slot. New systems should use deterministic formulas, lookup formulas, typed action steps, and registered capabilities instead. See the engine design notes (not published) §8.3 for the principle.

Legacy shape (still accepted and resolved by the loader):

"hooks": {
  "computeDerivedHook":   "system-id",
  "computeModifiersHook": "system-id",
  "transformRollHook":    "system-id",
  "formatRollResultHook": "system-id"
}

Resolution happens at load (pipeline stage 7) via getSystemHooks().

Do not introduce new uses. Routes for derivations that can't be expressed in pure Formula DSL:

  1. Fold into data (a stored field), if the value is set-once at entity creation.
  2. Use a declarative match/lookup formula for a finite table.
  3. Use a registered capability only when the core engine deliberately exposes one with a typed contract.

27. Migrations

When a system bumps its own version ('1.0' → '1.1'), declare the diff inline so existing rooms upgrade safely.

"migrations": [
  {
    "fromVersion": "1.0",
    "toVersion": "1.1",
    "operations": [
      { "kind": "rename",    "fromKey": "str", "toKey": "strength" },
      { "kind": "add",       "key": "wisdom", "default": 10 },
      { "kind": "remove",    "key": "obsolete_field" },
      { "kind": "transform", "key": "speed", "expr": "speed * 5" }
    ]
  }
]

Operations:

  • rename — value preserved, key path changes.
  • add — new key with default value.
  • remove — drop key entirely.
  • transform — recompute value through expression-eval formula.

operations: [] is a valid explicit no-op edge. Use it when a system content version changes but flat systemData does not: the version marker advances and the migration graph remains continuous without inventing a fake write.

Engine-level migrations (changes to EffectDuration shape, etc.) live in core code, not in manifests.

30. Overlay (homebrew on top of base)

A homebrew manifest is a JSON Patch (RFC 6902) array applied to a base.

{
  "schemaVersion": "1.0",
  "id": "my-homebrew",
  "name": "My D&D tweaks",
  "version": "0.1",
  "baseSystemId": "dnd5e-srd",
  "expectedBaseSystemVersion": "1.0",

  // Top-level definition becomes a JSON Patch array in DB storage:
  // (loaded as `loadManifest(patch, { base: parsedBase })`)
}

Patch operations: add / remove / replace / copy / move / test.

[
  { "op": "replace", "path": "/fieldGroups/0/fields/2/max", "value": 30 },
  { "op": "add", "path": "/conditions/-", "value": { ... new condition ... } },
  { "op": "remove", "path": "/autoModifiers/3" }
]

Engine compares expectedBaseSystemVersion with the current base version on load and applies semver policy:

  • patch updates auto-apply.
  • minor updates apply only if re-validate(composed) succeeds.
  • major updates require a manual migration step.

31. Bonus categories

Typed bonus stacking — D&D-style "status bonuses don't stack with status bonuses of the same name".

"bonusCategories": [
  { "id": "status",       "label": { "en": "Status" },       "stacking": "max-one" },
  { "id": "circumstance", "label": { "en": "Circumstance" }, "stacking": "max-one" },
  { "id": "item",         "label": { "en": "Item" },         "stacking": "max-one" }
]

Effect changes reference categories by id (bonusCategory: 'status'). The sheet-effects pipeline groups numeric changes by category + target field + mode, then applies add, max-one, or min-one. Unknown/omitted category ids keep ordinary additive behaviour. priority is accepted as category metadata, but the current resolver orders surviving changes by each change's own priority; category priority does not change the result yet.

32. Validation pipeline (what happens on load)

Each manifest goes through 8 stages. Stage 1-3 fail-fast (structure broken → nothing to check). Stages 4-8 accumulate errors; the author sees every issue in one fix-cycle.

Stage Validates Error kind
1. parse JSON syntax parse
2. Zod shape, types, regexes, enum values, required fields shape
3. overlay (optional) JSON Patch applies cleanly + composed shape Zod-valid patch, shape
4. references derivedKey / scopeId / sheetLayout / resourceId / modifyField.path refs resolve (path — поле или ключ ресурса: current/max/temp, ступени каскада); usableBy×scope compatibility reference
5. formulas derivedFields / action formulas / condition predicates parse formula
6. scope all {var} references resolve in visible environment scope
7. DAG derivedFields topo-sort terminates, no cycles dag
8. hooks legacy hooks.*Hook refs resolve to registered impls hook

For canonical pipeline architecture see the engine design notes (not published) §4.

33. Quick reference: writing a new system

  1. Pick a stable id (used in URLs, storage, references).
  2. Sketch fieldGroups — what data does a character carry?
  3. Add resources for current/max counters (HP, stress, …).
  4. Add derivedFields for computed values that other fields read.
  5. Add dataScopes if some fields are master-only / hidden-from-owner.
  6. Add actions — what does a character DO in this game?
  7. Add conditions — what status effects exist?
  8. Add sheetVariants on Sheets; add its optional fallback record only when unmatched tokens need an explicit sheetLayout. Verify player/creature selection.
  9. Add shared catalogs, entryConventions, and equipment when the sheet has structured items or spells.
  10. Add vision profiles and test them in an actual player view.
  11. Put representative Preview data in editorMeta._previewSeed.
  12. Run the full loader validation, then test owner/master/other permissions in a room before publishing the system.
  13. Load it through loadManifest(json) — read the errors, iterate.

Compact field tables

fieldGroup.layout or a sheet node’s layoutOverride: "table" renders each field as a name/value row with right-aligned numbers and subtle row dividers. Groups use two columns from 420 px of available width and one below that. Editing, permissions and calculated-value explanations use the normal field controls. The built-in D&D PC and NPC sheets use this for senses and movement.

List section headers

A collapsible containing one direct entryList, actionsList, conditionsList or traitsList shows its current count in the header, including zero. Counts follow the resolved list: action kind and viewer filtering, active conditions (including custom ones), and selected trait IDs. The same count appears when the section is grouped into a tab. Multiple independent lists keep their own headings rather than receiving an ambiguous combined count. For a single list, the section header also hosts the add command; conditions and traits retain their existing picker, permissions and editing callbacks.
