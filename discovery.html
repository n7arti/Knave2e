Как собрать полный контекст для агента

Этот маршрут позволяет пользователю или его агенту получить полный контекст для конкретной задачи: протокол подключения, язык системы, действия, предметные механики, реальные данные и проверку результата. Актуально на 13 октября 2026 года. Начать с выбора задачи можно в пользовательских сценариях.

1. Полнота состоит из пяти частей

  1. Полномочия: что пользователь поручил, к какому объекту есть доступ, какой канал подключён и какие операции он разрешает.
  2. Транспорт: адреса, авторизация, параметры, ответы, ошибки, версии, повтор запросов и получение результата.
  3. Языки данных: манифест, формулы, ActionDef, предметные носители, формат записей компендиума и статей.
  4. Контекст конкретной игры: фактическая definition, изменения правил, персонажи, ресурсы, предметы, активный стол и их версии.
  5. Доказательство: где сохранено, как импортировано/запущено, что изменилось.

Полнота не означает загрузить все документы платформы для одного броска. Она означает закрыть все зависимости требуемой операции. Если одного звена нет, агент может продолжить независимую подготовку, но не объявляет весь сценарий работоспособным.

2. Откуда начинать

Сначала проверьте version.json и выполните порядок обновления. Сохраните принятую версию комплекта и хеш его манифеста в паспорте задачи. Это отдельная версия документации, не версия моста и не редакция правил. При изменении прочитайте все пропущенные блоки agentAction и заново получите контекст затронутых операций.

Используйте адрес сайта из пакета подключения. Документы доступны без токена; к публичным страницам не нужно добавлять Authorization. API_BASE берётся отдельно из подключения: он может отличаться от адреса сайта.

Единый вход — оглавление агента. Пакет ассетов и ответ get_schema моста также дают ссылки на документацию. Относительные ссылки разрешаются от страницы, абсолютные пути — от origin сайта. В старых машинных документах встречаются внутренние пути docs/...: это обозначения источников, а не API. Используйте публичные адреса из следующего реестра.

3. Шаг первый: зафиксировать задачу и канал

Пользователь называет результат: подготовить JSON, сохранить записи, изменить систему или применить действие за столом. Агент записывает целевой ресурс и критерий готовности. Для неоднозначного имени сначала выполняется read-only поиск; при нескольких кандидатах нужен выбор пользователя.

  • Без подключения можно читать документы и готовить результат из переданного контекста.
  • PAT/MCP ассетов позволяет работать с доступными системами, компендиумами и поддерживаемыми файловыми операциями. Комнатой он не управляет.
  • Мост требует владельца комнаты с соответствующим доступом и открытого мастерского браузера. Чтение схемы также проходит через очередь комнаты.
  • Если задача затрагивает оба канала, нужны оба подключения. Токены не взаимозаменяемы.

Подробные правила и действующие ошибки доступа — в контракте выбранного канала. Наличие сохранённого секрета не заменяет проверки текущих полномочий.

4. Шаг второй: получить живой транспортный контракт

Для Asset API прочитайте страницу assets.html целиком: три части пакета, инвентарь маршрутов, схемы тела/ответа, пагинацию, загрузку файлов, версии и правила повторов. При доступном MCP сначала посмотрите фактические схемы инструментов. Названия операций REST и MCP не следует подменять друг другом; например, возможности передачи заголовка If-Match различаются.

Для моста:

  1. Отправьте get_schema по протоколу из bridge.html с roomId подключения.
  2. Сохраните requestId из ответа очереди и дождитесь результата команды.
  3. Сохраните version, protocol, authentication, endpoints, documentation и весь commands, включая параметры, readOnly и описание результата.
  4. Убедитесь, что требуемая команда и каждый необходимый параметр существуют.
  5. Прочитайте состояние активного стола перед изменениями.

Список названий команд без params не является полной схемой. get_schema не предоставляет автоматически definition всех систем, значения листов и все вложенные типы: для них нужен следующий шаг.

Не повторяйте мутацию из-за пустого результата очереди. Сначала дождитесь исполнения, затем проверьте состояние. Результат выдаётся один раз; сохраните его в контексте задачи. requestId — идентификатор результата, не гарантия дедупликации повторной отправки.

5. Шаг третий: собрать комплект языков

Для любой задачи с действием прочитайте вместе action-dsl-reference.json и glossary.json. Первый определяет поля и типы, второй — значения терминов, порядок создания и рецепты. master-pack.json помогает ориентироваться, но не заменяет пару исходных документов.

Затем добавляйте зависимости по задаче:

Если задача включает Дополнительно нужно
Новое поле, ресурс, состояние, derived или лист Манифест и процесс создания системы
Предмет, заряды, экипировку, превращение carrierContract референса и гайд автоматизации
Запись Action/Object компендиума Asset API и соответствующий формат вложенного systemData
Статью или медиа Контракт блоков статьи/медиа и файловые операции Asset API
Интерактивный выбор и цели Prompt/targeting в референсе и ограничения выбранного канала запуска
Реакцию, длительность, крит, повторение Их вложенные типы и порядок исполнения в референсе
Постановку на стол или тест комнаты Bridge, живой get_schema, гайд сцены
Работу человеком в редакторе Учебник действий и JSON-режим

Если прочитанная секция ссылается на ещё один тип, пример или контракт, прочитайте его до использования. Повторяйте, пока для каждого используемого поля известны тип, допустимые значения, место хранения и способ применения. Невозможность получить документ — незакрытая зависимость, а не разрешение придумать синтаксис.

6. Шаг четвёртый: прочитать конкретные данные

Для системы получите объект с полной definition, идентичностью и myRole. Для компендиума — его UUID, доступ, нужные записи, systemData, версии и ревизии статьи при работе с текстом. Пройдите все страницы нужной выборки, используя nextCursor; одна страница не доказывает отсутствие дубликата.

Для комнаты проверьте roomId, текущий tableId, активную систему, ID действующего и целей, текущие значения ресурсов и нужные предметы. Используйте read-only команды, объявленные живой схемой. Не считайте ответ get_items автоматически полным представлением любого вида инвентарных записей: сверяйте форму данных.

Для существующего действия приоритет имеет открытый черновик пользователя, если он передал его для правки. Не заменяйте его сохранённой версией без согласования. Для Object-шаблона нужно прочитать полный валидный снимок, а не восстанавливать его по названию и картинке.

Дайджест встроенной D&D 5e не описывает домашние изменения в её копии. Документированное имя ресурса ещё не означает, что этот ресурс объявлен в текущей системе. Проверяйте ссылки на всех уровнях.

7. Шаг пятый: проверить полноту и согласованность

Перед записью агент должен суметь ответить на каждый вопрос:

  • Какой именно объект изменяется и от чьего имени?
  • По какому контракту передаётся запрос и как получается результат?
  • Где живёт каждое поле: ActionDef, usable, definition, запись или вызов?
  • Все ли ключи и ссылки существуют в фактических данных?
  • Доступны ли нужные значения в момент вычисления и в выбранной ветке?
  • Есть ли в канале запуска параметры для источника предмета и ввода пользователя?
  • Что произойдёт при недостатке ресурса, последнем заряде и потере ответа?
  • Как прочитать результат и проверить его в интерфейсе?

Обязательный пример обнаружения ограничения: у зелья есть валидный usable, но execute_action не принимает sourceRef. Следовательно, подготовка предмета возможна, а проверка его расхода проводится из интерфейса предмета. Недостающий параметр нельзя добавить в ActionDef или считать неявным.

Порядок разрешения противоречий:

  1. Фактический ответ канала определяет доступные операции и параметры этого канала.
  2. Машинный контракт задаёт синтаксис действий; активная definition — реальные ключи.
  3. Проза и рецепты объясняют применение, но не добавляют отсутствующие поля.
  4. Ошибка загрузчика/редактора или наблюдаемое расхождение требует остановить зависимую запись и сообщить конфликт с точным примером. Не обходите её подстановкой похожего имени или ссылкой на старый пример.

Номер формата документа, версия payload записи Action, версия протокола моста и редакция игровой системы — независимые версии. Одинаковая дата документов не доказывает совместимость всех четырёх.

8. Шаг шестой: выполнить и подтвердить

Последовательность: прочитать актуальную версию → подготовить изменение → проверить структуру и ссылки → записать → перечитать → импортировать/запустить в выбранном канале → сравнить состояние до/после → передать результат.

Для definition сохраняется полный объект, для версионируемых записей учитываются версия и ревизия; подробности — в Asset API. Массовые операции используют документированные ограничения размера. REST-batch создания записей и bridge-batch имеют разные гарантии: не переносите атомарность одного на другой.

Для чистой подготовки остановитесь на проверенном артефакте и инструкции. Для внедрения недостаточно статуса HTTP: нужны сохранённый объект и проверка поведения в пределах согласованной задачи.

10. Если у ассистента нет доступа к URL

Пользователь может передать содержимое пары машинных документов, гайд автоматизации и релевантные части остальных контрактов файлами/текстом. Добавьте фактическую definition и объект задачи, укажите даты получения. Не передавайте персональный токен ассистенту, который только готовит JSON.

Если документы/ответы обрезаны, сначала получите недостающие разделы. Недостаток контекста отмечается явно. «Исчерпывающий комплект» означает прочитанные зависимости и данные, а не только список ссылок на них.
